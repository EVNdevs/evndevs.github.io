# Changelog

## 0.2.30 (2026-09-21)

- **Custom motors and per-port calibration from the Board view.** The gear on a motor port now really configures the board: EV3 Large / EV3 Medium / NXT, or **Custom…** (name, encoder counts per output revolution, rated voltage, no-load speed) — stored on the board, so a plain `Motor(port)` runs that motor from any host and after every reboot. The row has **Calibrate** (the ~5 s self-calibration, shaft free) and **Clear calibration**; it shows *calibrated 21 Sep 2026 14:02* / *not calibrated* / *calibration is for another motor*. Choosing a different motor for a port clears that port's calibration. The console sets the board's clock at connect so a calibration carries its date. Firmware: `evn.configure_motor()`, `evn.motor_config()`, `evn.calibration()`, `evn.clear_calibration()`; the calibration page is version 5 (older pages load; older firmware refuses a v5 page and a `calibrate()` there rewrites it as version 4, which loses the stored motor configurations: configure the ports again after re-upgrading). The Board view's motor picker used to be a note; the notes it held are replaced by what the board reports.

## 0.2.29 (2026-09-21)

**The overnight bug-bounty tournament's 36 fixes** (`docs/session/2026-09-21_bounty_tournament.md`): 59 findings, 59 confirmed, every one fixed, tested and adversarially reviewed; the two-wheel bar 172/172 and the owner's four hand checks green before this release. Highlights below; the firmware carries them all (`evn.version` 0.2.29).

- **Blocks: a Python block can spell `autostart(True)`** (B-036). The block editor imports a module name into a Python block only when its own list of the module's names holds it, and `autostart` was missing, so the unqualified call raised `NameError` on the board (`evn.autostart(True)` worked) although BLOCKS.md promises that nothing in the module is out of reach. The name is listed; `npm test` and `check.py` now derive the promised names from `evn_module.c`'s own table instead of a second hand-kept list, so the next module name cannot be missed (and the test no longer accepts the ever-present bare `import evn` as the import).
- **Docs and `help()` catch up with the firmware** (B-013, B-015, B-026). The API reference's Pybricks-deviations row says `settings()` returns `(max_voltage, stall_timeout)`, as the method row and the stub do; the pose-closed drive base is documented at its real rate (100 Hz with an IMU - every second DMP packet - 200 Hz on the wheels alone) in the stub, API.md and MICROPYTHON_API.md; `help()` has a `Pose` entry (constructor keywords, `position()`, `heading()`, `state()`, `reset()`, `sources()`, `close()`, the `with` form and `use_gyro`).
- **Firmware: `run_time()` refuses a `time` above 2147483647 ms** (B-035). The engine's deadline is a signed 32-bit compare, so `run_time(0, 10**10)` read as already elapsed: done at once and `then=` fired. A `time` above 24.8 days now raises `ValueError` instead of being clamped; the stub and API reference give the bound.
- **Run: a port another program holds is reported as such, before the run** (B-001-fix). When `mpremote` could not open the port at all (a previous Run terminal, a stale `mpremote`, the "Access is denied" state), the launcher reported "COULD NOT COAST THE MOTORS ... a motor the program left running is still running" for a program that never started. The launcher now probes the port first and, if it cannot be opened, says so, that the program was NOT started and the board untouched, and that the remedy is to close the other program on the PC (`taskkill /F /T` the stale python tree) - a power cycle only if nothing on the PC holds the port.
- **Firmware: `control.target_tolerances()` and `control.stall_tolerances()` read back the floats that were set** (B-032, B-024's sibling). The getters rounded to whole units, so `target_tolerances(position=0.25)` read back `(50, 0)` — a value the setter itself refuses — and 0.5 read 1. Speeds and the position tolerance are now floats; the stall time stays int ms. Stub and API reference updated.
- **Firmware: `Pose.reset()` takes keywords** (B-029). `pose.reset(heading=90)` raised `TypeError` although the docs and `help()` showed the keyword form; the binding took positionals only. `reset(x=, y=, heading=)` now works as documented, positionals unchanged.
- **Firmware: `control.pid()` reads the endpoint deadzone back as a float** (B-024). The getter rounded `integral_deadzone` to a whole degree, so the 0.75 default read as 1 and a legal 0.49 as 0 ("no deadzone"); it is now the float in degrees that was set (the other four values stay ints). Stub and API reference updated.
- **Firmware: a wheel-only `DriveBase` maneuver waits like `Motor` does** (B-005). `done()` / `wait=True` returned 2 s after the profiles ended even without `use_gyro`, while a wheel was still 2-5 deg off its aim (no stall): the 2 s escape written for a pose that never settles applied to the wheel tolerance test on every base. Without `use_gyro` the wait now ends only when both wheels are inside their tolerances (or passive) or on the stall timeout - `Motor.done()`'s meaning, as the docs had said; with `use_gyro` the 2 s escape stays (the trim moves the aims).
- **Firmware: a `Pose` dropped without `close()` no longer blocks every later `Pose(...)`** (B-008). The one-per-robot estimator kept running with no handle after a temporary, a function-local or a re-run cell, and the next constructor raised "a Pose object already exists" until Ctrl-D. The object now has a finaliser (as `Motor` has since the audit): a dropped `Pose` stops its service at the next collection, and the constructor runs one collection before it decides, so `def head(): return Pose(...).heading()` works on every call without a `gc.collect()` (bench 2026-09-21: five calls in a row). A bare temporary in the same statement scope (`Pose(...).heading()` then `Pose(...)`) can survive that one collection and still raise "already exists"; `Pose` is now a context manager - `with Pose(...) as pose:` closes on exit - and that, a function, or `close()` is the way to release it. Keep the object referenced while `DriveBase.use_gyro(True)` is on - the base holds no reference to it and raises at its next maneuver once the Pose is gone (stub and API reference say so).
- **Stub and API reference: `Motor.control.state()`** (B-003). The ADRC observer's 7-tuple (`reference_deg, x1_deg, x2_degs, x3_degs2, applied_mv, hold, assist`) existed in the firmware and the normative doc since 0.2.19 but not in the stub (Pylance flagged a working call) nor in the API reference (which steered testers to `model.state()`, the legacy observer). A host check now compares every evn class's stub with its C method table, and `help()`'s names with the C tables, so this class of gap fails the gate.
- *Make it permanent* (B-002 follow-ups): the confirmation names the variable boot.py really binds the module to (an existing `radio = evn.Bluetooth(2)` keeps its name), and `import evn as x` no longer counts as `import evn` (the added `bt = evn.Bluetooth(n)` would have raised NameError at boot and left the REPL off the module) - `import evn` is added beside it.
- **Firmware + extension: a Bluetooth module left carrying the REPL by `boot.py` can be reached again** (B-002). *Make it permanent* and Getting Started wrote the anonymous `evn.Bluetooth(2).repl(True)`: the driver instance kept the port with no Python handle, so every later `Bluetooth(2)` - a program's, or the Board view's Serial row after each console soft reset - raised `serial port 2 is already open` and the documented `bt.repl(False)` could not be followed. The firmware now keeps a per-port owner slot (set by construction, cleared by `close()`, by the object's finaliser and at soft reset, with one `gc_collect()` before deciding so adoption never depends on GC timing) and a plain `Bluetooth(n)` ADOPTS an attached carrier that no live object owns; two live objects still raise. *Make it permanent* now writes `bt = evn.Bluetooth(2)` / `bt.repl(True)` (an existing binding or the old anonymous form is recognised, not duplicated; `scripts/test_bootpy.js`), Getting Started shows the bound form and how to get the handle, CONSOLE_PROTOCOL.md's claim is true again.
- **`evn.core1_status()` gains a sixth element, `late`** (B-014): loop-body overruns of the 1 kHz engine (a body that ran past its 1 ms so two deadlines were pending when it came back — the count `exec_max_us` alone cannot give; `missed` counts only deadlines the alarm ISR itself skipped). Computed since the 2026-09-19 audit, exported nowhere until now; the console firmware's `Core1:` line ends `missed N, late N` too. The first five elements are unchanged.
- **The flash command verifies the bundled firmware before it reboots the board** (B-025). `EVN: Flash MicroPython firmware` (and the Board view's *Flash the bundled firmware*) showed `firmware/BUILD.txt` and then copied whatever bytes sat at `firmware/EVN_ALPHA_MicroPython.uf2`; a stale, truncated or half-synchronised file (the extension may live under OneDrive) flashed anyway, and a missing one threw after the board was already in BOOTSEL. The file is now checked - present, a whole number of UF2 blocks, the UF2 magic, and its md5 equal to BUILD.txt's `md5:` line - before `evn.bootloader()`; a failure refuses the flash with both hashes named and the board keeps running. `scripts/test_flash.js` drives the check with tampered pairs (in `npm test` and `check.py`).
- **Docs: a file write while a motor drives raises `OSError: [Errno 16] EBUSY`** (B-020). The API reference, Getting Started and the `Flash` stub still said the motion engine pauses for a write; since the 2026-09-19 audit the firmware refuses the write instead. The three surfaces now say what raises, when (a motor in `run()`/`dc()`, an unfinished maneuver or a moving track; holding, braked and coasting motors do not block it), and the idiom (write after the move, or catch and retry).
- **Firmware: `Bluetooth()` on a module that carries the REPL no longer accepts configuration it cannot apply** (B-017). With the REPL on the module (`boot.py`'s `repl(True)`, the standing state after *Make it permanent*) every later `Bluetooth(n, ...)` was attached warm and its `name`, `mode`, `addr`, `stay_in_command` and `baud` were parsed and silently discarded — `configured()` False, `config_errors()` empty, `print(bt)` showing a baud the port did not run. Now a plain `Bluetooth(n)` adopts the module as it stands at the port's own baud (reported truthfully), and any configuration argument raises `ValueError("the module carries the REPL; call repl(False) before changing its configuration")`.
- **Firmware: `Stop.COAST_SMART` follows Pybricks' condition** (B-018). The remembered target is the start of the next relative move only while the shaft (each wheel, for a `DriveBase`) still stands within twice its position tolerance of it; a shaft moved further while coasting — a slope, a hand, an unwinding gearbox — starts from where it is. Until now the aim won unconditionally and the whole displacement was travelled again on top of the next move.
- **`Compass.heading_confidence()` and `field_strength()`; the pose ignores a compass in a cancelled field** (B-011). A heading is an estimate and the owner's rule says it carries a measured confidence: `heading_confidence()` is 0..1 from this sample's |field| against the calibration's fitted radius (1 at the radius, 0 at 25 % off it; without a fitted radius a coarse 0.5 inside the Earth's 0.25..0.65 G, else 0). On the bench the compass 10 cm from the motors read 0.075 G — a quarter of the Earth's field, its direction set by the motors — with a plausible-looking `heading()`; it now reads confidence 0, and `Pose` drops such samples before the filter's gate so a steady stray field can no longer be laundered into the heading. While the field is rejected `Pose.sources()` omits `'compass'` and `Pose._stats()[8]` counts the dropped samples - the heading then has no absolute reference and drifts with the gyro/wheels until the field is the Earth's again.
- **Firmware: `I2C.stats()` `errors` no longer climbs on healthy identifies** (B-012). Every driver identifies its chip by an ID-register read, and on an empty port (or at the other chip's address in the compass's two-chip identify) that read NACKs by design; the layer counted each one as a bus error (+2 per `Compass()`, +1 per constructor on an empty port, and 4/s for as long as an unplugged sensor was re-probed), which the header and the API had promised it would not. Identify transactions now run inside `hal_i2c_identify_begin/end()` in all eleven standard drivers, the compass and the IMU: an address NACK there is not counted; a data NACK, a timeout (still recovered and counted) and any mux failure are.
- **Firmware: `Motor.run_time()` takes `time`, as Pybricks promises** (B-016, with three follow-ups: the profile is compared with the engine's caps in shaft units, `run_time(0, t)` holds the measured angle with a time-only `done()`, keyed on the command so a later move landing on the same angle is still judged by its tolerances). `run_time(0, 1000)` (a timed hold, what the *run motor for ms at speed 0* block generates) returned after ~3 ms: the distance was zero, and a zero-distance profile is complete on its first tick. The engine now has a timed move (`cmd_min_ms`): the move is not `done` and its `then=` does not fire before `time` has passed; `run_time(0, t)` holds the motor **where it is** (never the previous aim, which sent a shaft settled a degree short through the stiction path - once for ten minutes on the bench) and its `done()` is time-only; a non-zero `run_time` sizes its distance to the speed and acceleration the controller will actually allow at the present pack voltage, compared in shaft units so `gears=` are respected, so a limit shortens the distance, never the duration. `then=Stop.NONE` stays untimed (it hands over at speed).
- **Firmware: `Pose.reset()` no longer makes a gyro-following drive base drive off by itself** (B-010). With `DriveBase.use_gyro(True)` a `Pose.reset(x, y, heading)` after a maneuver moved the estimate but left the follower's ideal robot where it was, so the loop drove the wheels up to 98 mm (the trim limit) with no command and `done()` True. A reset is a re-framing, never a command: the pose service now re-anchors the ideal on the new pose exactly as `DriveBase.reset()` does. To close an offset an outside reference revealed, follow the reset with an explicit `straight()`/`turn()` (stub, API reference and MICROPYTHON_API.md say so).
- **Firmware: a Core 0 stall no longer loses the pose its travel, and the pose-closed drive base no longer over-drives after one** (B-009). A stall longer than 100 ms while a maneuver runs (a big-int power, `json.dumps` of a long list, a 16-port `I2C.scan()`) used to make the pose estimator drop that step - the wheels kept turning under Core 1 but their travel never reached the position (154 mm lost over a 379 ms stall at 400 mm/s on the bench) - while `DriveBase.use_gyro(True)`'s follower integrated the same commanded travel into its ideal and then drove the robot 98 mm past its leg with `done()` True. The estimator now integrates a gap's exact encoder travel as one arc (heading from the wheel difference, position along the mean heading), so the two agree; beyond 2 s both re-anchor. `Pose._stats()` gains an eighth counter (gap steps). Host: `test_pose.py` gap checks and a seventh fixture block; `test_drive_follow.py` models the old and the new rule (the old reproduces the 98 mm).
- **The end of a program run from the extension coasts every motor** (B-001). Pybricks ends a program with the motors stopped, and the firmware does the same when `main.py` ends; a program started with **Run** (Ctrl+F5, desktop or browser IDE) is sent through the raw REPL, where the board has no program end - so `m.run(200)` as the last line, a `run_angle(..., wait=False)` still in flight or a traceback half-way through a move left the wheel turning after "program finished" until Ctrl-C, the user button or the pack. Both runners now end the program the way `main.py` ends: the desktop launcher (`scripts/evn_run.py`) writes the same 0x03 emergency stop the Ctrl-C path uses straight to the port the moment `mpremote run` returns, finished or raised, and the web terminal sends `evn.stop_all()` on the raw REPL it still holds - neither is a soft reset, so the REPL that follows still has the program's variables. The terminal says `program finished; the motors are coasting` (or `the motors are coasting` under a traceback); when the board cannot be reached for the coast it says `COULD NOT COAST THE MOTORS` in red and the status bar shows an error instead of a stop that did not happen. Host tests: `tools/host_tests/test_evn_run.py` (the desktop launcher's call order with fakes) and `scripts/test_terminal.js` (the web terminal against a scripted raw-REPL board; part of `npm test` and `check.py`). Also found by that test: the web terminal dropped a program's first output bytes when they arrived in the same read as the raw-paste acknowledgement, and a print-and-exit program could hang the terminal - `RawRepl.exec()` and the runner now keep those bytes.
- **Firmware: the 1 kHz tick never branches into flash, and a gate proves it after every link** (B-004). Two callees of the tick were flash-resident and invisible from the source: `time_us_64()` behind an inline wrapper, fetched on every tick before the exec stopwatch (so `exec_max` never showed it; the tick period read 991/1009 us instead of 1000/1000), and the `memcpy` the compiler emits for two struct copies, whose SDK shim sat in flash. The per-tick body is now its own SRAM function timed with the 32-bit timer word, `PICO_MEM_IN_RAM=1` moves the memcpy shim to SRAM, and `tools/check_tick_veneers.py` walks the tick's whole call graph in the linked ELF after every build (and in `check.py`), failing on any branch out of SRAM.

## 0.2.27 (2026-09-20)

- **Firmware: the pose estimator no longer learns a pivot's after-shock as a gyro bias.** With `DriveBase.use_gyro(True)` the estimator's heading had walked 5–8° off the floor within a minute of pivots while the pose reported a fraction of a degree (0.2.26's recorded residual). The USB tether was the blocker for running the floor test, not the cause of the residuals: untethered, the ~1 mm chassis walk per pivot is unchanged.

## 0.2.26 (2026-09-20)

- **`DriveBase.use_gyro(True)`: the drive base closes its loop over `evn.Pose`.** Until now a maneuver was two profiled wheel moves, exact in wheel space and open loop over the chassis: the scrub of a turn in place, a dragged cable and the gyro's drift added up over minutes (the floor ended several degrees off after 45 maneuvers). With a `Pose` built on the same two motors, every maneuver and `drive()` is now trimmed at 200 Hz so the *robot* follows the path the program asked for: the base keeps the pose an ideal robot would have (command-exact, continuous across chained maneuvers) and corrects the body-frame error with the RAMSETE law into each wheel's reference (the profiles stay the feedforward, the ADRC the wheel loop). `done()` waits for the pose to settle inside `follower()` tolerances (1 mm, 0.3°). New: `use_gyro()`, `follower(...)` (the loop's knobs: `b` 400, `zeta` 0.7, `k_min` 4, correction bounds, trim limit and slew, tolerances), `pose_error()`. Host model (`tools/pose/test_drive_follow.py`): 40 chained maneuvers with scrub, a 0.5 % wheel mismatch, cable drag and gyro drift close to under 0.5 mm / 0.11° on the estimate for wheel lags up to 60 ms; a 20 mm lateral offset closes to 0.35 mm within one straight. What the pose cannot see (a translation the encoders do not turn for) is not corrected. **Relative moves chain from the aim** (owner, 2026-09-20): `Motor.run_angle` / `run_time` and every `DriveBase` maneuver now count from the exact target the motor is holding after the previous position command — Pybricks' rule, the reference while actively controlled — so ten `run_angle(200, 90)` are 900° and chained maneuvers are exact in wheel space, instead of each inheriting the previous settle's residual inside the 1° `done()` tolerance; a coasted, braked, stalled or hand-forced (> 45°) shaft still starts from where it is. **Two implicit behaviours other stacks give for free** (owner, 2026-09-20): `Motor.settings(stall_timeout=)` (default 1 s) ends a `wait=True` move once the motor has been stalled that long — the hold keeps pushing and `stalled()` is True, the program is no longer stuck on a jammed gripper (0 = wait forever, Pybricks); and `use_gyro(True)` waits for `IMU.ready()` (the DMP's gyro calibration, 8–25 s into stillness) before arming the chassis loop, as a Pybricks hub calibrates its IMU before any program runs. **`color_match() -> (Color, confidence)`** on `ColorSensor` and `GestureSensor` (owner, 2026-09-20: a classification comes with its confidence): the colour `color()` gives plus the margin to the runner-up in `detectable_colors()` — 1.0 on the colour, 0.0 halfway between two — from one reading, so a program can threshold a match. **Floor acceptance, 2026-09-20** (`tools/bench/mpy_drivebase_pose.py`, the owner reading a taped mark, the robot on a USB tether): five 30 cm / ±45° ladders with `use_gyro(True)`, 40 maneuvers in a minute, run twice. On the pose both runs closed within 2.3 mm and 0.2° with every maneuver under 0.8 mm / 0.4°, where one ladder without the loop drifted 4° (the encoders-only baseline) and the trims steered the wheels 13–27° against scrub. On the mark: 8 mm forward / 4 mm left / a fraction of a degree the first time, **17 mm left / 9 mm forward / 5° clockwise the second** — two residuals the loop cannot see and this release does not fix: the chassis walks about 1 mm on every turn in place (the same 20 mm after twenty about-turns at full and at half turn acceleration; the tether drags from the back), and on the second run the estimator's heading itself drifted ~5° from the floor in 57 s while reporting 0.02°, so the loop steered faithfully to a wrong heading. Use `use_gyro(True)` for the heading; expect centimetres, not millimetres, of position over a minute of pivots until an outside reference is in the loop. **The default straight acceleration is now 75 % of the motor limit** (about 1230 mm/s² on two Mediums): at the full 1630 mm/s², five out-and-backs left the robot 8 mm off the mark from tyre slip that neither the encoders nor the pose can see; at 1230 and 820 it came back within 1–3 mm. Turn acceleration is unchanged (the pivot's ~1 mm walk per about-turn is the same at half acceleration: the third contact point and the tether, not slip). Design: `docs/DRIVEBASE_POSE_FOLLOW.md`.

## 0.2.25 (2026-09-20)

- **Firmware 0.2.25: the endpoint hunt is fixed.** A `run_target()` / `track_target()` that came to rest just outside the endpoint deadband could shake for a second at 2–3° either side of the target (a ±2–3° cycle at about 4 Hz; in the overnight endurance run one motor did it on a quarter of its arrivals). The breakaway assist, which pushes a shaft stuck short of its target free, released its push only after 1° of travel at speed — by then a free EV3 Medium was doing ~140 deg/s and coasted 2° past. At a stopped target it now lets go at the first encoder edge of travel (0.4°), and the shaft settles inside the deadband. Behind a moving reference nothing changes. Measured on the bench with the hunt reproduced on demand (`tools/bench/mpy_arrival_trace.py`: 12 hunting moves of 32 → 0 in 128), the free-shaft sweep alternating with 0.2.24 (182 / 174 against 179 / 184 of 192, the run-to-run scatter), `run(0)` settle 0 residuals in 40, a 25-minute four-axis endurance run with zero hunts.
- **Known and recorded**: on a motor whose calibration installed a measured encoder phase table the shaft can rest 0.6–0.7° from its target (inside the 0.75° deadband) and `angle()` then reads ±1; where that happens depends on the target's phase in the encoder cycle, not on the direction. `docs/ADRC_IMPLEMENTATION.md` §6g.

## 0.2.23 (2026-09-19)

- **Firmware 0.2.23: `main.py` starts from the user button.** After a power-on or reset the board no longer runs `main.py` at once: it waits, LED blinking fast, for a press of the user button, and when the program ends the next press runs it again (the Pybricks way; a robot with a program on it never moves the moment it is switched on, and needs no PC to run again). Anything typed at the port during the wait — the extension connecting, `mpremote`, Enter in a terminal — gives the REPL instead. *Upload and run now* still starts the program immediately (`evn.reset(start=True)`); `evn.autostart(True)` in `boot.py` restores the start-at-power-on for an unattended board; a 2 s hold of the button reboots a running program and the board waits again. ## 0.2.20 (2026-09-18)

- **Firmware 0.2.20: the pose estimator with an IMU on a real, moving robot.** With wheels and an IMU the prediction is now hybrid — speed from the wheels, yaw rate from the gyro, the gyro bias learned from the wheel difference whenever the robot is not turning. The plan's inertial speed prediction integrated the accelerometer, which under the running drive motors carries 1.4–1.9 m/s² of vibration (peaks 4–9 m/s²) against robot accelerations below 1 m/s²: the estimated speed jumped ±0.5 m/s, half the wheel updates were gated out, and every move ended 30–130 mm off. On the rig's floor moves (90° turns, 20 cm straights, 90° pivots, each returning to its start) every move is now within 6 mm of the encoders and turns in place within 1.2 mm (`docs/POSE_ESTIMATION_DESIGN.md` §6).
- **New `Pose(..., imu_offset=(x_mm, y_mm))`**: where the IMU sits, forward and left of the axle mid-point; a tape-measure value is enough. It removes the centripetal and tangential terms a turning body adds at a lever arm (used by the sets without wheels).
- **Filter robustness**: a wheel update that failed its χ² gate used to stay rejected for ever once the prediction had run away; after ten rejections running the speed prior is dropped and the wheels are taken (as the magnetometer update already did for the heading). The service's and the filter's angle wraps were `while` loops that never end on a huge or infinite heading; both are bounded now. `Pose._stats()` (bench diagnostic) exposes the gate counters.
- **Mounting note**: the filter takes the body frame the `IMU` / `Compass` objects publish, so a module's `axes(top=, front=)` must be set from its silkscreen before the `Pose` is built (the rig's IMU is upside down, `axes(top='-z')`; its compass has the chip's −x on top). A compass within about 10 cm of the motors reads the wheel angles (0.45 G in the heading plane per wheel turn) and cannot be calibrated or used as a heading source.
- **Encoders-only pose benched in the air** (three runs, every sample within 2.1 mm and 0.8° of the dead-reckoned encoders) and **bench scripts** `tools/bench/mpy_pose_wheels.py`, `mpy_pose_imu_offset.py`, `pose_wheels_metrics.py`; samples are kept in RAM and written to the board's flash after the motors coast (a flash write during a move stalls the 1 kHz motion loop for a sector erase).

## 0.2.15 (2026-09-18)

**Every one of the fifteen EVN Standard Peripherals is now bench-validated** (the per-device dates are in `docs/STANDARD_PERIPHERALS.md` §1). The documentation, the stubs, the snippets, the examples and the board's own `help()` no longer say "not validated on hardware" anywhere, and the stub's signatures were re-derived from the firmware bindings method by method — about a hundred of them disagreed with the C (a keyword the binding does not take, a getter typed as a setter, an `int` where the firmware returns a `float`, an optional argument shown as required).

**The I2C transport recovers by itself.** A transaction that timed out used to leave the RP2040's controller mid-transfer with bytes in its FIFOs, so the next read on that bus returned a stale byte and reported success (on the rig, a colour sensor's ID read 0x00 instead of 0x4D after a forced overrun). The layer now aborts, resets the controller, clocks a held SDA free with nine SCL pulses and a STOP, and re-initialises the bus after every timeout; it drops the multiplexer's channel cache after any failed transaction, so a multiplexer that lost its channel is re-selected instead of never; and it sizes the deadline to the transfer (1 ms + 40 µs per byte, at least 5 ms), so a long transfer no longer times out for being long. The three outcomes are now distinguishable from Python: `OSError(ENODEV)` — nothing answered at that address; `OSError(EIO)` — the device answered but refused a byte; `OSError(ETIMEDOUT)` — the bus was held and has been reset. `evn.I2C(port).stats()` reports `((errors, recoveries, stuck), (...))` per bus.

- **`evn.I2C`**: `scan()` never lists 0x70; 0x70 (the board's two multiplexers, which answer on every port) is refused on every port and 0x6A on port 16 (the battery charger) with `ValueError` — a stray write to either would have re-routed the whole bus or reprogrammed charging. `writeto()` takes 1..4096 bytes. New `stats()`. `_deadline(us)` is a private bench hook, documented as such.
- **`Compass`**: new `calibrate_cancel()` — a refused `calibrate_stop()` raises `ValueError` and **keeps collecting**, so a program can turn the sensor further and stop again, or give up cleanly. New `overrun()` (the QMC5883L's dropped-measurement flag) and `self_test(negative=False, raw=False)` (HMC5883L, at the gain the datasheet prescribes). `data_rate()` and `range()` return floats on both chips. `bias()` is refused below 4.0 Ga, where the strap saturates. The closed-object message is now `"Compass is closed"`, and a second `Compass(port)` on an open port keeps the calibration and the `north()` reference.
- **`Bluetooth` and `UART`**: new `readline(timeout=5000)` on both — the next line without its trailing `b"\n"` and without a `b"\r"` in front of it, or `None` on timeout; only the line leaves the receive buffer, so bytes that arrived behind it stay for the next `read()`. `timeout=0` never waits, a negative timeout raises `ValueError`, and a line longer than 255 bytes never completes: `readline()` times out and `overflow()` counts what was dropped. New `overflow()` on both (read-and-clear), and `UART.repl()` was missing from the stub.
- **`ColorSensor`**: `gain()`, `integration_time()`, `wait_time()` and `thresholds()` now return only once a sample measured under the new setting exists. `interrupt()` documented as `True` at the default persistence of 0 ("every cycle") — pass 1 or more for a flag that means "the clear count left the window".
- **`GestureSensor`**: `read_gesture(timeout=5000)` accepts the keyword the docs always promised (it raised `TypeError` before); a negative timeout raises `ValueError`. `status()[4]` is the chip's `GCONF4.GMODE` bit. `gesture_detail()`'s first three values are direction names or `None`, not integers.
- **`ADC`**: the default range is **±4.096 V** and the documentation no longer says ±6.144 V. `raw()`, `voltage()`, `read()` and `age()` take the input positionally.
- **`EnvSensor`**: documented that normal mode delivers a reading every measurement time plus the standby (40.5 ms at the defaults, ≈ 24.7 per second), while `measurement_time()` is the datasheet's worst case.
- **`TouchArray`**: the three `thresholds()` forms are documented as the binding implements them — `thresholds()` reads channel 0, `thresholds(3)` reads channel 3, `thresholds(12, 6)` sets every channel **including the proximity channel 12**, and `thresholds(3, channel=2)` raises `TypeError`. `overcurrent()` reports a fault seen since the object was opened, because the driver recovers from it by itself.
- **`Display`**: `text(col, row, s, invert=False)` accepts the keyword and returns the number of characters written; `on(enable=True)`, `zoom(enable=True)` and `all_on(enable=True)` take the argument optionally; `flip()` and `invert()` are getters as well as setters. Documented: the panel's RAM is not written while a hardware scroll runs (the first drawing call stops it and repaints, a new `scroll()` sends the stop first), `flip()` does not repaint, the constructor can take up to ≈ 740 ms on a freshly plugged panel, and `mirror()` is dropped by Ctrl-D.
- **`MatrixLED` / `SevenSegmentLED`**: `addr=None` picks the class default (0x71 / 0x74) and `addr=0x70` is refused with `"addr must be 0x71..0x77 (0x70 is the board's I2C multiplexer)"`. `SevenSegmentLED.number()` refuses an int outside −999..9999 and NaN / infinity instead of showing a saturated value; `MatrixLED.text(on=0)` is refused. The closed-object message names the class (`"MatrixLED is closed"`, `"SevenSegmentLED is closed"`) and a full pool says `"port %d: no free LED display slot (at most 4)"`.
- **`IMU`**: `tilt()` is documented with its real range, (−180, 180] on both axes, so an upside-down module is not read as level; `screen_orientation()` reports each event once; `dmp(rate=None)` keeps the rate in force; `stationary()` and `ready()` raise while the module is out; `settings(heading_correction=)` is clamped to 1..3600. The gyro filter values 250 Hz and 3600 Hz are refused (they select the chip's 8 kHz internal rate and break the DMP's time base), and an `evn.I2C` scan of the IMU's port pops one FIFO byte, which the driver heals.
- **`Servo.close()` and `UART.close()` are new.** A `Servo` object used to hold its channel until the next soft reset, so a program could not hand a servo port to an `RGBLED` strip (or re-open it with another profile) without Ctrl-D; a `UART` object held its serial port the same way. `close()` releases the claim on both — the servo's pulse stops and its pin goes low, the serial port keeps running and keeps its queued bytes — and every later call on the closed object raises `ValueError("Servo is closed")` / `ValueError("UART is closed")`. A second `UART` on a port an open object holds now says so (`OSError("serial port %d is already open")`), and a `Servo` constructor waits up to 10 ms for a just-closed strip to hand the channel back. `evn.I2C.scan()` also stops on a port whose probe timed out, instead of carrying the rest of the scan out against the bare bus.
- **`Servo` / `RGBLED`**: the servo channel has one owner — `RGBLED(n)` raises while a `Servo` object holds the port and the other way round; a servo port pulses nothing until the first `Servo` object is built; `disable()` is sticky but a new object drives its port again. `RGBLED`'s `invert` is keyword-only, and a blink or animate step below 2 ms is refused (the pattern is stepped by the 1 kHz poll).
- **Documentation and tooling**: `docs/API.md` and the README no longer describe the peripherals as pending a bench check; every peripheral snippet imports what it uses on its first line, and there are new snippets for the ADC, environment sensor, touch array, gesture sensor, LED matrix, seven-segment display, Bluetooth module and UART. `examples/08_standard_peripherals.py` was read against the bindings and every call that would have raised is fixed (`read_gesture(timeout=)`, `text(invert=)`, a seven-segment `text()` of letters the chip has no glyph for, an unguarded `calibrate_stop()`). The board's `help()` lists every class with its methods. The four block examples — `colour_line`, `spirit_level`, `compass_lights` and `bluetooth_grabber` — are named in the README and the getting-started guide, which also say that every peripheral has blocks.

Three fixes: `SevenSegmentLED(port)` looked for the board at the wrong I2C address (0x71, the matrix's) and would never have found it — it now uses the board's 0x74 (`addr=` still overrides); `addr=0x70` (the board's own I2C multiplexer) is refused; `keys()` would have returned garbage because this chip mis-sequences a repeated-start read. A negative integer larger than 999 now shows `-999` instead of losing its sign. `MatrixLED` (the 8×8 board) has not been on hardware yet.
- `Display` bench-validated on the EVN OLED (2026-09-17; the panel is an SSD1315): every text and drawing call checked in the frame, the panel read by eye (logo, text grid, flip, invert, contrast, shapes, console scroll, hardware scroll, blink, zoom), unplug / replug with the picture restored by itself; the packaged firmware will include it from the next build. Four fixes: the display's setup sequence was never sent (a byte too long for the driver's buffer), so `Display(port)` could not have started any panel; an unplugged display was never noticed and a replugged one stayed dark — the driver now reads the panel's status every 100 ms, re-runs the setup when the panel was reset, and gives a freshly plugged panel time to wake up before configuring it; `print()` never used the bottom row (it scrolled a line early); `command()` takes up to 32 bytes. New: `Display.mirror(True)` copies the board's stdout — the REPL, every `print()`, tracebacks — to the panel, with or without a USB host.
- Second-pass audit of all twelve standard-peripheral drivers (2026-09-17): `DistanceSensor.raw()` now reports the signal and ambient rates the right way round and no longer calls a "no update" range a "sigma fail"; `EnvSensor` setting changes are applied once the chip is idle (they could be ignored by the chip before); `GestureSensor` powers the chip on before enabling its engines; `IMU` no longer times out during its ~360 ms DMP load on a busy bus and drops a raw-mode gyro bias when switched to the DMP; `RGBLED.blink()` requires `[on, off, ...]` pairs. Bench-check guidelines per device in `docs/STANDARD_PERIPHERALS.md` §18.

## 0.1.4 (2026-09-16)

## 0.1.3 (2026-09-16)

- Firmware rebuilt with the ADRC control law as the default (active disturbance rejection; self-calibrating, no per-motor tuning), `control.law()` to read or switch it (`"adrc"` / `"pid"`), and the observer at half bandwidth while holding at the endpoint (no more endpoint hunting on the EV3 Medium).
- Default limits at the fastest validated moves: acceleration 2400 deg/s² (EV3 Large) / 3000 deg/s² (EV3 Medium); a calibrated port's speed limit is its measured no-load speed when that is higher, so `run(100)` in percent mode is not clamped. The firmware caps every move at what the motor can do at the present battery voltage.
- `calibrate(wait=False)` starts a port without blocking; a later `calibrate()` on that port joins it, so several ports calibrate from one call.
- `done()` is true within 1° (was about 11°); `stalled()` / `load()` come from the ADRC's disturbance estimate (a calibrated unknown motor gets a working stall flag).
- `calibrate()` measures the motor's no-load speed as well (two-amplitude pulse test, about 4.5 s) and returns `(b0, tau_ms, v_break_mv, v_f_mv)`; a calibrated port's `full_speed()` is that measurement. `calibrate_speed()` removed (it duplicated `calibrate()`).
