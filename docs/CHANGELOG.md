# Changelog

## 0.2.63 (2026-10-09)
- **Firmware: `Pose` runs on the motor core.** Its filter steps now run on the board's second core beside the motors, on the motors' own 1 ms clock, instead of in the gaps of your program: a busy program (a long `print`, a big calculation) no longer delays them, and your program gets that time back - on a bench board (EV3 Medium wheels and an IMU, no compass) a plain loop beside a running `Pose` takes about 10 µs a pass where 0.2.62 took about 49 (9.8 against 49.1, one run of 0.2.62), the `Pose`'s own share of a pass about 1.7 µs against 39.5, `DriveBase.distance()` about 80 µs a call against 418, and a drive program's polling loop about 0.19 ms a pass against 2.76; against the same firmware with the filter still in your program's gaps, over eight alternating runs, each of them is faster well beyond run-to-run noise (9.8 against 20.5 µs, 1.7 against 10.3, 80 against 138, 194 against 630). A bare loop with nothing open runs about as on 0.2.62 (3.56 against 3.53 µs a pass, +0.8 %: Known in this release, below). What you can see: on the wheels alone it steps 200 times a second (177-194 before; checked on the host models); while the program is busy it keeps stepping on the wheels every 5 ms after the first 15 ms, the heading over that time then the IMU's kept readings' as before (`Pose._stats()` counts those steps in its seventh number, where it used to count one per busy moment); and a `DriveBase` with `use_gyro(True)` reads the pose up to a millisecond after it was measured, so `pose_error()`'s forward error reads up to about 1 mm more while cruising at 300 mm/s. If the motor core has stopped on a fault (every motor coasted), `Pose(...)`, `reset()` and `settings(...)` raise `OSError` (EIO: the motor core did not answer) instead of waiting; `settings()` still raises `ValueError` for a value out of range.
- **Firmware: the Python heap is 128 KB (139 KB in 0.2.62).** The drive base's position estimate (`Pose`) now runs on the board's second core, the motor core (below), from the board's RAM instead of flash, and its code - about 16 KB with the filter's arithmetic - comes partly from the heap: `gc.mem_free()` reads about 11 KB less, and a program that ran within 11 KB of 0.2.62's limit may now raise `MemoryError`. Four of the motor core's own files are now compiled for size rather than speed to make the room; that core's stack grows from 2 to 3 KB in memory the heap never used.
- **Firmware: the motor engine's 1 ms tick now runs inside its timer interrupt, so nothing else the second core does can delay it** - the groundwork for moving the drive base's position estimate onto that core. Motors move as before: four alternating runs of the loaded move set against 0.2.62 on two boards and three motor models gave the same move times, settling and accuracy, every move done, no missed or late tick; the tick itself takes up to 2-3 µs longer on four motors. Two safety changes come with it: if the second core ever crashes, every motor coasts at once instead of holding its last power, and a file write gives up after 5 ms (the write fails as busy, nothing written) instead of waiting for ever on a second core that does not answer. It takes about 1.8 KB of the board's static RAM (the Python heap: above).
- **Firmware: about 6.6 KB of the board's static RAM freed for the work that moved to the second core.** The 2 KB the C library kept for `malloc` (which nothing in the firmware calls) is gone, and `math.erf`, `math.erfc`, `math.lgamma` and `math.gamma` run from flash instead of RAM: their results are unchanged, bit for bit, and each call takes longer - `erf` / `erfc` about 5-11 µs, `lgamma` / `gamma` about 23 µs (59 / 53 / 51 / 59 µs a call instead of 49 / 47 / 28 / 35). The firmware now refuses to build with less than 1 KB of static RAM free.
- **Firmware: a second `Pose(...)` on the same sources takes the running one over** (the owner's ruling of 2026-10-02, as for `Motor`, `Servo` and `IMU`). A `main.py` that builds its own `p = Pose(...)` at the top used to raise `OSError("a Pose object already exists")` from the second press of the user button on, because Python still held the last run's `p` when the new run built its own. Now a `Pose(...)` on the same wheel ports, IMU port and compass port as the running one replaces it: the new object starts from its own arguments (x, y and heading 0, as `close()` then `Pose(...)` would), and every call on the older one raises `ValueError("Pose was replaced by a newer Pose on the same sources")`, `print()` shows `Pose(replaced)` and its `close()` does nothing. A `DriveBase` that held the older Pose treats it as closed (its next maneuver with `use_gyro(True)` raises; build the base with `pose=` the new one, or with `imu=`). A `Pose(...)` on other sources still raises while one runs: one Pose per robot. Which sources count as the same, and that the new object starts afresh instead of carrying on the running estimate, are the owner's rulings (2026-10-09). Checked on host models and on a bench board (the take-over in about 5 ms).
- **Firmware: a second `IMU(port)` takes the running IMU over instead of starting it again** (the owner's ruling of 2026-10-02, as for `Motor` and `Servo`). Building `IMU(3)` again - a re-run cell, a helper that makes its own, the Board view's IMU row beside an `IMU` you built at the console prompt - used to reset the chip and reload its DMP (about half a second), put `heading()` back to 0 and make the IMU learn its gyro bias again (`ready()` False for up to 25 s without a stored calibration), and an `evn.Pose` or `DriveBase(..., imu=3)` lost its gyro for that time. Now the new object takes the IMU as it runs, in a few milliseconds: the heading with its `reset_heading()`, the learnt bias and `ready()`, `settings()`, the rate and `axes()` stay, and a Pose keeps its IMU without a gap. The older object is **replaced**: every call on it raises `ValueError("IMU(3) was replaced by a newer IMU(3)")`, `print()` shows `replaced`, its `close()` does nothing (before, an older object's `close()` put the newer one's IMU to sleep), `DataLog.add()` refuses it, and a `calibrate(wait=False)` it had running stops with nothing stored. `IMU(port, calibrate=True)` still starts the IMU again, as before. **A program run again from the user button keeps its IMU, at heading 0**: the IMU the last run left running keeps its DMP, its learnt gyro bias and `ready()` - no half-second restart and no wait for the bias - and every setting the last run gave it (the rate, `axes()`, `dmp()`, `filter()`, `ranges()`, `settings()`; an IMU an imported module set up stays set up, as Python does not run the module again), and the new run starts at `heading()` 0, as Pybricks resets the heading when a program starts (before, every button run started the IMU again: about half a second, the default settings, and `ready()` False until the bias was learnt again). A `calibrate(wait=False)` or `calibrate_gyro()` the last run left running stops with nothing stored. The run's first `IMU(port)` starts at heading 0 too, as on a first run, unless the run already called `reset_heading()`. A setting one run changes is still in force in the next, so set what your program needs at its start. A Run from the editor still starts the IMU again (it begins with a soft reset). Checked on host models and on a bench board (the take-over in about 1 ms, the DMP not restarted, the heading kept; the run boundary's heading 0 with the settings kept); a real button run twice, by hand, is still to come.
- **Firmware: a program run again from the user button starts a kept `DriveBase` and `Pose` afresh** (the owner's ruling of 2026-10-02, as Pybricks starts every program afresh). A `DriveBase` (and its `Pose`) that an imported module made - Python keeps the module between button runs and does not run it again - used to carry on from the last run: `distance()`, `angle()` and the pose's x, y and heading went on from where the last run left them, while the IMU above now starts at heading 0. Now each button run starts such a base at `distance()` and `angle()` 0 with no maneuver in force, and its `Pose` at x, y 0 with the heading 0, as `reset()` does (with a compass among the Pose's sources too: the compass then holds the new zero, as after `reset()`); the base's `settings()`, `follower()`, `use_gyro()` and `pose`, and the Pose's sources, settings and learnt gyro bias are kept. Nothing moves. A kept `Motor` reads `angle()` 0 again when it was built with `reset_angle=True` (the default), as a fresh `Motor(port)` does; built with `reset_angle=False` it keeps its count. Checked on host models and on a bench board (the kept base at 0 mm / 0°, its Pose at 0, 0, the wheels' angles 0, nothing moved); with a compass among the Pose's sources the new zero's hold is still to be checked on the board.
- **Firmware: `IMU.heading_confidence()` says when the heading can still creep after `ready()`.** `ready()` keeps its quick start (about a second of stillness with a stored calibration), but the IMU's DMP measures its gyro bias itself only 8 to 25 s into stillness (about 14 s on the bench), and until then the heading builds on the stored calibration's bias - off by its drift with temperature, so it could creep a fraction of a degree (up to ~1.5° before 0.2.60). Without a stored calibration, a module whose gyro bias happens to be small reads `ready()` at once while its heading drifts at that bias, degrees in those seconds. `heading_confidence()` reads `0` before `ready()`, `0.5` once ready while the DMP has not measured its gyro yet, and `1` once it has (raw mode: `1` as soon as `ready()`; `dmp(True, gyro_cal=False)` stays at `0.5`, its DMP never measures one). To start from the steadiest heading, wait for `1` with the robot still and a time limit, then `reset_heading()`. The firmware sees the DMP's measurement in the DMP's memory, which it reads (about 0.5 ms of the I2C bus) in place of every other once-a-second temperature reading while the robot is at rest, and only until it has seen it (`temperature()` is then refreshed every other second); never while the robot moves or a motor drives. On a bench board without a stored calibration (three runs) the 1 came 0.7-0.8 s after the DMP's own yaw stepped down from about 0.6°/s to under 0.02°/s, every time; with a stored calibration it is still to be checked on the board.
- **Firmware: an `IMU` in raw mode takes its turn with the other devices, unless a `Pose` reads it.** Since 0.2.59 the firmware reads the `IMU` and the `Compass` - the two sensors `evn.Pose` reads - ahead of every other I2C device, and an `IMU` in raw mode (`imu.dmp(False)`, 1000 readings a second by default) was read first too, whether a `Pose` used it or not: with many devices open it took the other sensors' turns and much of the program's time (on the bench board with nine devices open, that change measured on its own before 0.2.59 shipped left a plain loop about 11 % of the board's time where 0.2.58 gave it about 26 %; in the released 0.2.59 a loop beside a raw-mode `IMU` and the same devices took about 1.7 times as long as on 0.2.58). Now a raw-mode `IMU` goes first only while a `Pose` - or a `DriveBase` built with `imu=` - reads it, when it is part of the robot's position; otherwise it is read in turn like any other device, also when it is a second `IMU` beside a robot's. The `IMU` in its default DMP mode and the `Compass` still go first. In a host model of the bench rig with a raw 1 kHz `IMU` open and no `Pose`, a program keeps about 42 % of the board's time where it kept 12 %, and the raw `IMU`'s readings are as fresh as on 0.2.58 (about 8 ms at worst); with a `Pose` on it, the `IMU` is read as often as on 0.2.59-0.2.62 (about 4 ms at worst), at that release's price. The switch follows the `Pose`: it starts when the `Pose` is built and ends when it closes. Read in turn, a raw-mode `IMU` also collects the bias average it takes by itself before `ready()` (after a second still) more slowly, so that average now lasts up to 2 s - about 400 readings with nine devices open, where 0.2.59-0.2.62 took its 1000 in about 1.2 s and counting them in turn would have taken about 5 s; with a `Pose` on it, it is always the whole 1000 readings, about 1.2 s as before. Read in turn, its `stationary()` also looks over a longer time: its last 250 readings, about 1.2 s with nine devices open, so it turns `True` up to about 2.5 s after a motion stops (0.2.58 did the same); with a `Pose` on it, about 0.6 s. On a bench board with six devices open (a shorter turn than the nine above), a busy loop beside a raw 1 kHz `IMU` with no `Pose` took 4.8 ms against 10.2 ms on the firmware before it (11.6 ms on 0.2.62), and the price the change accepts was measured there too: `imu.calibrate_gyro(500)` in raw mode with no `Pose` took 753-762 ms against 634-636 ms (18-20 % longer), and `ready()` after `imu.dmp(False)` came 350-450 ms later (about 3.0 s against 2.5-2.6 s). The board with all nine devices is still to be measured.
- **Firmware: `imu.calibrate_gyro()` waits for as long as its readings keep coming.** It gave up after a total time worked out from the sample rate, and an `IMU` read in turn with many other devices collects more slowly than its rate (in the host model of the bench rig, 500 raw readings take about 2.5 s against the 1.5 s it allowed - 0.2.58 ran out the same way). It now raises `OSError` only when no new reading has come for three periods plus the other devices' turns plus 0.1 s (about 0.15 s with nine devices open).
- **Firmware (needs the firmware of this release): a `VL53L1X` region the chip cannot select reads `status()` `'roi fail'`.** ST's range status 13 (UM2555 section 4.2: the sensor could not use the `roi()` with that centre) read `'min range fail'`, the name of status 3, so the two could only be told apart by `raw()[1]`; it now has its own name, in `status()` (and so in the Board view's live row when it shows `status`), in a `DataLog`'s `status` column and in the console firmware's `x vl` line. Every other status keeps its name. A program that tested `status() == 'min range fail'` to catch a bad region tests `'roi fail'` now (`raw()[1] == 13` works on both).
- **Firmware: the CM22-2230 12V 1:49 is re-measured on two bare motors.** Its library figures came from one motor driving a gear train; they now come from six calibrations of two motors with nothing on their shafts. For a CM22-2230 user: before its first `calibrate()` the motor starts from a closer guess of its strength (b0 5900, was 5650; the six calibrations read within 8 % of it), and `Model.state()` works from the motor's own running friction (0.25 V; the gear train's was 0.40 V). The 1:49 ratio is now verified - one output turn, then ten, against a mark on the shaft - so 3136 counts per output revolution stand (to what a mark read by eye after ten turns can show). A port you have calibrated keeps controlling from its own calibration and does not need calibrating again; only `Model.state()`'s estimate takes the new friction figure. The limits stay 700 deg/s and 5000 deg/s²; on the battery the motor runs about 760 deg/s. Do not hold it stalled.
- **Board view: the IMU row works beside your own `IMU` object.** With an `IMU(port)` of yours at the console prompt - held by a name, a list or dict, an object's attribute such as `robot.imu` or an imported module, up to two levels down (`robots[0].imu`), also after `from evn import *` - the row's live values and its calibrate / clear buttons use your object instead of replacing it; when yours is out of reach (a temporary such as `IMU(3).heading()`), calibrate and clear take the IMU back without restarting it. The row also follows your next `IMU(port)` after you close one.
- **Blocks:** the IMU's *is still* / *is ready* block has a third choice, *has calibrated its gyro (steadiest heading)* (`imu.heading_confidence() == 1`).

## 0.2.62 (2026-10-03)
- **Firmware: the Python heap is 139 KB** (140 KB in 0.2.61): the board now keeps at least 1 KB of its static RAM free for the work planned on the second core (0.2.61 kept about 0.2 KB), and that kilobyte comes from the heap. `gc.mem_free()` reads about 1 KB less; a program that ran within 1 KB of 0.2.61's limit may now raise `MemoryError`.
- **Firmware: the CM22-2230 12V 1:49 joins the motor library** (`Motor(port, model="cm22_49")`, `evn.configure_motor(port, "cm22_49")` or the Board view's gear): a 22 mm 12 V planetary gearmotor, 185 rpm, with a 16 ppr hall encoder on the motor shaft, so 16 x 4 x 49 = 3136 counts per output revolution. The port is capped at its 12 V rating (above the battery, so the cap never binds: on the battery it runs about 740 deg/s), it runs on the EV3 Large control class with `control.limits()` 700 deg/s and 5000 deg/s², and its encoder counts with its drive on the EVN cable. **Its figures were measured through an external 1:1 gear train with backlash** (three `calibrate()` runs of one unit: b0 5309-5951, τ 16.5-18.4 ms, running friction 388-406 mV, 1136 deg/s at 12 V against the seller's 1110): the library's model of the motor, its first-guess b0 and its limits come from those, and the motor will be measured again on a bare shaft, which may change them. Calibrate it once (`m.calibrate()`, about 11 s, shaft free) before its first closed-loop move. On the bench (through the train, calibrated) it finished every move within 0.22° of its target (two encoder counts; 0.08° on average) and ran the same moves 12-17 % faster than the same motor configured as `"custom"`, which starts from a lower acceleration (2400 deg/s²). Do not hold it stalled: on a full battery its stall reaches the gearbox's 8.5 kg·cm maximum (by the seller's table) and about 5x the motor's rated current. Another ratio of the family (1:3.5 to 1:510) is a custom motor with 16 x 4 x the ratio counts.
- Tools: the host tests know the CM22-2230 (the runaway guard, a clean calibration on the real `adrc.c`, the plausibility band against its three records and a drive base up to its τ ceiling, its plant block on the real observer); its bare-shaft re-profile is a tracked bench (`tools/bench/mpy_cm22_profile.py`, `cm22_ripple_metrics.py`, and `mpy_cm22_turns_hand.py`, which checks the 1:49 against a mark on the output shaft); its closed-loop check is one too (`tools/bench/mpy_cm22_moves.py`: run_angle at two accelerations, `run()` steps, a hold and a stall under a voltage cap below the motor's friction, with `cm22_moves_metrics.py`).
- **Firmware: a drive base with an IMU and a compass is back to 0.2.59's speed.** On the bench's drive-base board (EV3 Medium wheels, an IMU and a compass, the release gate's four alternating runs), a Python loop beside an `evn.Pose` runs 13 % faster than on 0.2.61, the Pose's own cost per pass is 14 % lower, `DriveBase.distance()` 4 % and a drive program's polling loop 2 % faster; against 0.2.59 every one of them is now within run-to-run noise (the polling loop the same to the microsecond), and a loop reading the IMU and the compass is 6 % faster than on 0.2.59. 0.2.61's known issue for those rows no longer applies. The code is 0.2.61's; what moved is where some of it sits in memory.
- **Known in this release:** as in 0.2.61, on a Pololu 25D (or any motor whose rotor cogs) moves overshoot their target more than on 0.2.59 and report `done()` a little later - 0.2.60's change that brings the shaft to rest in the detent nearest its target; the final position error is better than on 0.2.59. On the bench board's two Pololu 25D (the loaded move set, eight alternating runs): overshoot 1.23° against 0.2.59's 0.75° (0.2.61: 1.27°), `done()` 477 ms against 472 ms; the CHR-GM16 and the EV3 Medium move as on 0.2.59. Accepted by the owner ("Accept both, publish", 2026-10-03); the release gate's record is `firmware/GATE.json`.

## 0.2.61 (2026-10-03)
- **Firmware: a motor holding a load keeps holding it when the next command comes.** `hold()`, and `run_target()` / `run_angle()` from a hold, used to forget the load the controller had learned (an arm's weight, something it pushes against), so the shaft sagged until it had learned the load again. The load is now kept, and a move's start push adds to it; an arm lowered under its load no longer drops a few degrees after it stops. `hold()` holds the load itself: an arm that `run_target()` lifted into place no longer keeps the extra push that turning against friction needed. An arm clearly light enough for friction to hold (under about 85 % of the motor's breakaway) is held with no push at all, as before; one close to the breakaway, where the controller cannot tell whether friction alone would hold it, is held with a push just beyond it (about 1.15x the breakaway), so it cannot slip. After a slow lift (about 20°/s or slower, where the motor moves in small jerks) `hold()` cannot tell the arm's weight from the friction and keeps the whole push that lifted it: the arm does not sag, but a light arm is held with a push it does not need. A motor that nothing blocks, calibrated with its mechanism, runs as before (on the CHR-GM16 its moves now settle a fraction of an encoder step differently, below); against an end stop (`run_until_stalled()`, a target 3° or more past the stop) it runs as before until `hold()` re-targets it there. A `DriveBase`'s wheels keep the previous behaviour. The carried load is measured so far only in the host model, for the EV3 Medium and Large (an EV3 Medium holding an arm at 1.5x its breakaway: `hold()` sagged 6° before, 0° now, after a fast or a slow lift; an arm just over its breakaway, lifted into place and settled: 2.7° on average before, 0.07° now); the Pololu 25D, CHR-GM16 and JGA25 are not yet measured under a load, and on the CHR-GM16 and JGA25 the load is learned only on moves of about 50°/s or faster. - **Firmware: a Pololu 25D (or any motor whose rotor cogs) now comes to rest in the detent nearest its target, not in the one before it.** At the end of `run_angle()` / `run_target()` / `track_target()` the controller used to let the shaft settle as soon as it was within half a detent of the target, and a shaft still short of the crest in front of the target's detent then fell back a whole detent (6.2 deg): on the bench's short set 22 of port 1's 80 moves ended more than 1.5 deg short of the target against 14 long, on both 0.2.58 and 0.2.59, and the shaft often wobbled for a second or more before it settled. Motors that do not cog (LEGO, JGA25, CHR-GM16) run exactly as before, and so does a Pololu until the controller has learnt where its detents are (its first coasted rest after power-up or `calibrate()`). The Python heap is 141 KB (142 before) to make room. - **Firmware: a `DriveBase` keeps one clock for both wheels.** When one wheel is held back - blocked, or loaded more than it can drive - its move waits (as a `Motor` has since 0.2.22), and now the other wheel waits with it and both carry on together, so the robot stays on the line or arc it was asked for instead of turning about the held wheel; `drive()` does the same, also when your program calls it over and over in a loop (a line follower, a **drive at** block in a forever loop). A straight `drive()` from standstill is unchanged.

## 0.2.59 (2026-09-28)
- **Firmware (needs the firmware of this release): a second `Motor(port)` or `Servo(n)` takes the port over** instead of raising `OSError(EBUSY)`. The motor coasts, a `calibrate(wait=False)` the older object started stops, a `DriveBase` it is a wheel of closes (with the `Pose` it built), and every call on the older object raises "Motor(n) was replaced by a newer Motor(n)" while its `close()` does nothing - so re-running a cell simply works. The Board view takes a port back the same way from a `Motor` or `Servo` made at the console (Stop, run, calibrate, configure; a servo's Stop stops your own `Servo` where it is); reads and refused commands take nothing.
- **Firmware: `stop()`, `brake()` and `close()`** on a `Motor` or `DriveBase`, and `evn.stop_all()`, return once the motor has taken the command (at most 2 ms), so a file write straight after them is no longer refused.
- **Firmware: `calibrate()` after a finished `calibrate(wait=False)` returns that run's result at once** instead of measuring again for ~12 s. A command that moves, holds or stops the motor in between (its `DriveBase`, `close()`, a take-over, `evn.stop_all()`) drops the result; reads and settings do not. `evn.configure_motor()` checks the model and numbers before the port: a wrong spec raises `ValueError` even while a `Motor` holds the port.

The phase starts over after `calibrate()` and after a `configure_motor()` that changes the motor, and after three rests in a row far from it that agree with each other (counts lost with the cable out); `calibrate()` returns once the new phase is taken, about 0.3 s later.
- **Firmware: the IMU starts right side up.** The DMP now starts from the face the module lies on, so an upside-down module reads upside down from the first sample: `tilt()`, `up()` and `heading()` are correct from the start, and `heading()` no longer swings about 145° in the first seconds. Until the orientation agrees with the accelerometer, `heading()` follows the gyro's turn about the vertical (a turn made then is kept) and `ready()` waits; with a stored calibration `ready()` comes in about a second. `sample_rate()` and `dmp()` on a module without a stored calibration no longer freeze `heading()` and `ready()`; with `dmp(True, gyro_cal=False)` `ready()` comes in about 2 s (without a calibration `heading()` then drifts at the gyro's raw bias, about 1° per 5 s on the bench unit: `calibrate()` removes it).

With the IMU in its default DMP mode, `evn.Pose`'s heading through a pause of up to 140 ms is the gyro's, not the scrubbing wheels' (about 1° per 0.1 s pause in a fast turn before).

With few devices open the cost is small. A faster I2C engine that gives this time back is in development.

## 0.2.42 (2026-09-26)
- **Firmware (needs the firmware of this release): the encoder is calibrated in each direction of turning, on every motor.** A quadrature encoder's four edges never sit exactly a quarter cycle apart, and `calibrate()` has measured where they are since 0.2.20 - but only with the 1 kHz control tick, which cannot time an edge that shares a millisecond with another. ## 0.2.38 (2026-09-25)
- **Firmware: a `DriveBase` builds and owns its `Pose`.** `DriveBase(left, right, wheel_diameter=62.4, axle_track=170, imu=3)` (and `compass=`, `declination=`) builds the pose estimator from the base's own geometry: the two motor ports, the wheel diameter and axle track, each motor's `positive_direction` and the motors' gears. - **Firmware: `use_gyro(True)` checks the geometry, and the base holds its `Pose`.** With a pose on the base it re-checks that the geometry still agrees; with none it adopts a running `Pose` after the same full check; with no pose anywhere it raises `ValueError("use_gyro needs a pose: DriveBase(..., imu=port) builds one, pose= takes yours")`. The base now keeps a reference to the `Pose`, so the old "keep the Pose object referenced" caveat is gone; a `Pose` closed under the loop turns `use_gyro` off with an `OSError` at the next maneuver. `robot.close()` closes a `Pose` the base built, never one the program built and gave it; a `Pose` an old base built and hands to a new base on the same wheels (`pose=old.pose`) comes with its ownership, so the new base's `close()` closes it. Migration: the old form (a `Pose` built by the program, then `use_gyro(True)`) still works and is now validated.
- **Blocks: the *robot follows its gyro* block generates the new form.** The *set up robot* line carries `imu=N` and `drive_base.use_gyro(True)` follows; there is no separate `pose = Pose(...)` line, and the pose is `drive_base.pose`. The snippet, the stub, `examples/03_robot/robot_complete.py` and the API reference show the same program.
- **Firmware (internal): the follower reads the pose through an engine seam.** `motion/pose_estimate.h` is the new interface between a pose engine and the chassis follower, so other base types (a car, a holonomic base) and other follower laws can come later on the same seam; nothing a tester sees changes. Host: `test_pose.py` gap checks and a seventh fixture block; `test_drive_follow.py` models the old and the new rule (the old reproduces the 98 mm).
- **The end of a program run from the extension coasts every motor** (B-001). Pybricks ends a program with the motors stopped, and the firmware does the same when `main.py` ends; a program started with **Run** (Ctrl+F5, desktop or browser IDE) is sent through the raw REPL, where the board has no program end - so `m.run(200)` as the last line, a `run_angle(..., wait=False)` still in flight or a traceback half-way through a move left the wheel turning after "program finished" until Ctrl-C, the user button or the pack. Both runners now end the program the way `main.py` ends: the desktop launcher (`scripts/evn_run.py`) writes the same 0x03 emergency stop the Ctrl-C path uses straight to the port the moment `mpremote run` returns, finished or raised, and the web terminal sends `evn.stop_all()` on the raw REPL it still holds - neither is a soft reset, so the REPL that follows still has the program's variables. The terminal says `program finished; the motors are coasting` (or `the motors are coasting` under a traceback); when the board cannot be reached for the coast it says `COULD NOT COAST THE MOTORS` in red and the status bar shows an error instead of a stop that did not happen. Host tests: `tools/host_tests/test_evn_run.py` (the desktop launcher's call order with fakes) and `scripts/test_terminal.js` (the web terminal against a scripted raw-REPL board; part of `npm test` and `check.py`). Also found by that test: the web terminal dropped a program's first output bytes when they arrived in the same read as the raw-paste acknowledgement, and a print-and-exit program could hang the terminal - `RawRepl.exec()` and the runner now keep those bytes.
- **Firmware: the 1 kHz tick never branches into flash, and a gate proves it after every link** (B-004). Two callees of the tick were flash-resident and invisible from the source: `time_us_64()` behind an inline wrapper, fetched on every tick before the exec stopwatch (so `exec_max` never showed it; the tick period read 991/1009 us instead of 1000/1000), and the `memcpy` the compiler emits for two struct copies, whose SDK shim sat in flash. The per-tick body is now its own SRAM function timed with the 32-bit timer word, `PICO_MEM_IN_RAM=1` moves the memcpy shim to SRAM, and `tools/check_tick_veneers.py` walks the tick's whole call graph in the linked ELF after every build (and in `check.py`), failing on any branch out of SRAM.

## 0.2.15 (2026-09-18)

**Every one of the fifteen EVN Standard Peripherals is now bench-validated** (the per-device dates are in `docs/STANDARD_PERIPHERALS.md` §1). The documentation, the stubs, the snippets, the examples and the board's own `help()` no longer say "not validated on hardware" anywhere, and the stub's signatures were re-derived from the firmware bindings method by method — about a hundred of them disagreed with the C (a keyword the binding does not take, a getter typed as a setter, an `int` where the firmware returns a `float`, an optional argument shown as required).

**The I2C transport recovers by itself.** A transaction that timed out used to leave the RP2040's controller mid-transfer with bytes in its FIFOs, so the next read on that bus returned a stale byte and reported success (on the rig, a colour sensor's ID read 0x00 instead of 0x4D after a forced overrun). The layer now aborts, resets the controller, clocks a held SDA free with nine SCL pulses and a STOP, and re-initialises the bus after every timeout; it drops the multiplexer's channel cache after any failed transaction, so a multiplexer that lost its channel is re-selected instead of never; and it sizes the deadline to the transfer (1 ms + 40 µs per byte, at least 5 ms), so a long transfer no longer times out for being long. The three outcomes are now distinguishable from Python: `OSError(ENODEV)` — nothing answered at that address; `OSError(EIO)` — the device answered but refused a byte; `OSError(ETIMEDOUT)` — the bus was held and has been reset. `evn.I2C(port).stats()` reports `((errors, recoveries, stuck), (...))` per bus.

- **`evn.I2C`**: `scan()` never lists 0x70; 0x70 (the board's two multiplexers, which answer on every port) is refused on every port and 0x6A on port 16 (the battery charger) with `ValueError` — a stray write to either would have re-routed the whole bus or reprogrammed charging. `writeto()` takes 1..4096 bytes. New `stats()`. `_deadline(us)` is a private bench hook, documented as such.
- **`Compass`**: new `calibrate_cancel()` — a refused `calibrate_stop()` raises `ValueError` and **keeps collecting**, so a program can turn the sensor further and stop again, or give up cleanly. New `overrun()` (the QMC5883L's dropped-measurement flag) and `self_test(negative=False, raw=False)` (HMC5883L, at the gain the datasheet prescribes). `data_rate()` and `range()` return floats on both chips. `bias()` is refused below 4.0 Ga, where the strap saturates. The closed-object message is now `"Compass is closed"`, and a second `Compass(port)` on an open port keeps the calibration and the `north()` reference.
- **`Bluetooth` and `UART`**: new `readline(timeout=5000)` on both — the next line without its trailing `b"\n"` and without a `b"\r"` in front of it, or `None` on timeout; only the line leaves the receive buffer, so bytes that arrived behind it stay for the next `read()`. `timeout=0` never waits, a negative timeout raises `ValueError`, and a line longer than 255 bytes never completes: `readline()` times out and `overflow()` counts what was dropped. New `overflow()` on both (read-and-clear), and `UART.repl()` was missing from the stub.
- **`ColorSensor`**: `gain()`, `integration_time()`, `wait_time()` and `thresholds()` now return only once a sample measured under the new setting exists. `interrupt()` documented as `True` at the default persistence of 0 ("every cycle") — pass 1 or more for a flag that means "the clear count left the window".
- **`GestureSensor`**: `read_gesture(timeout=5000)` accepts the keyword the docs always promised (it raised `TypeError` before); a negative timeout raises `ValueError`. `status()[4]` is the chip's `GCONF4.GMODE` bit. `gesture_detail()`'s first three values are direction names or `None`, not integers.
- **`ADC`**: the default range is **±4.096 V** and the documentation no longer says ±6.144 V. `raw()`, `voltage()`, `read()` and `age()` take the input positionally.
- **`EnvSensor`**: documented that normal mode delivers a reading every measurement time plus the standby (40.5 ms at the defaults, ≈ 24.7 per second), while `measurement_time()` is the datasheet's worst case.
- **`TouchArray`**: the three `thresholds()` forms are documented as the binding implements them — `thresholds()` reads channel 0, `thresholds(3)` reads channel 3, `thresholds(12, 6)` sets every channel **including the proximity channel 12**, and `thresholds(3, channel=2)` raises `TypeError`. `overcurrent()` reports a fault seen since the object was opened, because the driver recovers from it by itself.
- **`Display`**: `text(col, row, s, invert=False)` accepts the keyword and returns the number of characters written; `on(enable=True)`, `zoom(enable=True)` and `all_on(enable=True)` take the argument optionally; `flip()` and `invert()` are getters as well as setters. Documented: the panel's RAM is not written while a hardware scroll runs (the first drawing call stops it and repaints, a new `scroll()` sends the stop first), `flip()` does not repaint, the constructor can take up to ≈ 740 ms on a freshly plugged panel, and `mirror()` is dropped by Ctrl-D.
- **`MatrixLED` / `SevenSegmentLED`**: `addr=None` picks the class default (0x71 / 0x74) and `addr=0x70` is refused with `"addr must be 0x71..0x77 (0x70 is the board's I2C multiplexer)"`. `SevenSegmentLED.number()` refuses an int outside −999..9999 and NaN / infinity instead of showing a saturated value; `MatrixLED.text(on=0)` is refused. The closed-object message names the class (`"MatrixLED is closed"`, `"SevenSegmentLED is closed"`) and a full pool says `"port %d: no free LED display slot (at most 4)"`.
- **`IMU`**: `tilt()` is documented with its real range, (−180, 180] on both axes, so an upside-down module is not read as level; `screen_orientation()` reports each event once; `dmp(rate=None)` keeps the rate in force; `stationary()` and `ready()` raise while the module is out; `settings(heading_correction=)` is clamped to 1..3600. The gyro filter values 250 Hz and 3600 Hz are refused (they select the chip's 8 kHz internal rate and break the DMP's time base), and an `evn.I2C` scan of the IMU's port pops one FIFO byte, which the driver heals.
- **`Servo.close()` and `UART.close()` are new.** A `Servo` object used to hold its channel until the next soft reset, so a program could not hand a servo port to an `RGBLED` strip (or re-open it with another profile) without Ctrl-D; a `UART` object held its serial port the same way. `close()` releases the claim on both — the servo's pulse stops and its pin goes low, the serial port keeps running and keeps its queued bytes — and every later call on the closed object raises `ValueError("Servo is closed")` / `ValueError("UART is closed")`. A second `UART` on a port an open object holds now says so (`OSError("serial port %d is already open")`), and a `Servo` constructor waits up to 10 ms for a just-closed strip to hand the channel back. `evn.I2C.scan()` also stops on a port whose probe timed out, instead of carrying the rest of the scan out against the bare bus.
- **`Servo` / `RGBLED`**: the servo channel has one owner — `RGBLED(n)` raises while a `Servo` object holds the port and the other way round; a servo port pulses nothing until the first `Servo` object is built; `disable()` is sticky but a new object drives its port again. `RGBLED`'s `invert` is keyword-only, and a blink or animate step below 2 ms is refused (the pattern is stepped by the 1 kHz poll).
- **Documentation and tooling**: `docs/API.md` and the README no longer describe the peripherals as pending a bench check; every peripheral snippet imports what it uses on its first line, and there are new snippets for the ADC, environment sensor, touch array, gesture sensor, LED matrix, seven-segment display, Bluetooth module and UART. `examples/08_standard_peripherals.py` was read against the bindings and every call that would have raised is fixed (`read_gesture(timeout=)`, `text(invert=)`, a seven-segment `text()` of letters the chip has no glyph for, an unguarded `calibrate_stop()`). The board's `help()` lists every class with its methods. The four block examples — `colour_line`, `spirit_level`, `compass_lights` and `bluetooth_grabber` — are named in the README and the getting-started guide, which also say that every peripheral has blocks.

## 0.1.3 (2026-09-16)
