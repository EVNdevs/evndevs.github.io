# Changelog

## 0.2.25 (2026-09-20)

- **Firmware 0.2.25: the endpoint hunt is fixed.** A `run_target()` / `track_target()` that came to rest just outside the endpoint deadband could shake for a second at 2–3° either side of the target (a ±2–3° cycle at about 4 Hz; in the overnight endurance run one motor did it on a quarter of its arrivals). The breakaway assist, which pushes a shaft stuck short of its target free, released its push only after 1° of travel at speed — by then a free EV3 Medium was doing ~140 deg/s and coasted 2° past. At a stopped target it now lets go at the first encoder edge of travel (0.4°), and the shaft settles inside the deadband. Behind a moving reference nothing changes. Measured on the bench with the hunt reproduced on demand (`tools/bench/mpy_arrival_trace.py`: 12 hunting moves of 32 → 0 in 128), the free-shaft sweep alternating with 0.2.24 (182 / 174 against 179 / 184 of 192, the run-to-run scatter), `run(0)` settle 0 residuals in 40, a 25-minute four-axis endurance run with zero hunts.
- **Known and recorded**: on a motor whose calibration installed a measured encoder phase table the shaft can rest 0.6–0.7° from its target (inside the 0.75° deadband) and `angle()` then reads ±1; where that happens depends on the target's phase in the encoder cycle, not on the direction. `docs/ADRC_IMPLEMENTATION.md` §6g.

## 0.2.24 (2026-09-20)

- **Firmware 0.2.24: `Display.flip()` repaints again.** The segment re-map (A0h/A1h) only applies to data written after it (SSD1306 §10.1.8), so the 0.2.23 change that skipped the repaint left a live panel upside down *and mirrored* until the next drawing call; `flip()` is back to rewriting the frame (about 30 ms). Owner's eye check pending on the bench (the bench cannot read the panel).
- **`GestureSensor` names gesture mode instead of "not responding".** An APDS-9960 with an object inside its gesture threshold from power-up (a module lying face down) enters gesture mode before its first colour/proximity cycle; `proximity()`, the colour getters and `age()` now raise `OSError("gesture sensor on port N is in gesture mode (...) ... engines(gesture=False)")`, deterministically from the first call; with every engine off `age()` raises a `ValueError` naming the engines.
- **Bench and tools**: `tools/bench/mpy_scan_id.py` identifies every I2C device on the 16 ports by its ID register (run it first; the owner plants decoys); `mpy_mpu6500_axes_settle.py` measures that `IMU.axes()` no longer restarts the DMP (first new-frame packet in 4 ms against 128° of yaw and 19 s of settling for a real restart); `mpy_encoder_max_rpm.py` (encoder at a Medium's no-load maximum, 59/59); `mpy_endurance.py` + `endurance_metrics.py` (a multi-hour four-axis run with one line per move, and a run-down phase); `mpy_run.py --stream`. The 16-case sweep tool builds the harness again (`--build` had been producing the console build since the CMake option restructure) and takes `--axis-models` so any mix of motors on the four ports is judged on its own model's rows.

## 0.2.23 (2026-09-19)

- **Firmware 0.2.23: `main.py` starts from the user button.** After a power-on or reset the board no longer runs `main.py` at once: it waits, LED blinking fast, for a press of the user button, and when the program ends the next press runs it again (the Pybricks way; a robot with a program on it never moves the moment it is switched on, and needs no PC to run again). Anything typed at the port during the wait — the extension connecting, `mpremote`, Enter in a terminal — gives the REPL instead. *Upload and run now* still starts the program immediately (`evn.reset(start=True)`); `evn.autostart(True)` in `boot.py` restores the start-at-power-on for an unattended board; a 2 s hold of the button reboots a running program and the board waits again. New `evn.reset(*, start=False)`, `evn.autostart([on])`, `evn._chip_reset()`.
- **The editor saves before it sends.** The Run and Upload buttons in the editor title, the explorer menu and the Projects view handed the command a file and skipped the save that the palette command did, so the board ran the file as last saved while the editor showed newer text. Every entry point now saves the open document first.
- **One invisible way onto the RPI-RP2 drive closed**: the SDK default that reboots the board into BOOTSEL when a host sets 1200 baud (the Arduino IDE's upload touch) is off; `evn.bootloader()`, the extension's flash command and `picotool` are unaffected. Site issue #1 ("comes back as RPI-RP2 after a power-button off/on with USB attached") is under investigation with `tools/power_cycle_watch.py`; the firmware has no path of its own into BOOTSEL and the owner's bench board does not reproduce it.

## 0.2.22 (2026-09-19)

- **Firmware 0.2.22: `evn.DriveBase`** — two `Motor` objects driven as a robot with the Pybricks `robotics.DriveBase` API: `DriveBase(left, right, wheel_diameter, axle_track)`, `straight(mm)`, `turn(deg)`, `curve(radius, angle)` and `arc(radius, distance= | angle=)` (both Pybricks sign conventions, see the reference), `drive(speed, turn_rate)`, `stop()` / `brake()`, `distance()` / `angle()` / `state()` / `reset()`, `done()` / `stalled()`, `settings(...)`. A maneuver is two profiled moves on one time base (the wheel with the longer travel leads, the other is scaled by the ratio of travels, both started on the same 1 kHz tick), so a straight is straight and an arc is an arc; on the floor every 30 cm out-and-back and every ±45° turn closed within 1.3 mm and 1.3° (gyro-fused `Pose` as the truth), the two wheels' profiles end within 5 ms of each other, endpoints within 1° on 41 of 42. **Defaults are the weaker wheel's `control.limits()`** (about 770 mm/s and 520 deg/s on two Mediums with 62.4 mm wheels: the floor ladder closed as cleanly there as at 40 %); lower them with `settings()` for a heavier robot. A direct `Motor` command on one wheel coasts the other (Pybricks); a new `DriveBase` on the same motors takes them over. `then=Stop.NONE` is refused (use `drive()`); no gyro heading loop yet.
- **Tester surfaces**: a **Robot** block category (set up robot, drive straight, turn, drive an arc, drive at, stop, speeds, reset; *robot distance / angle / is done / is stalled* under Sensing; a Python block that mentions `drive_base` gets it created) with the `drive_base` blocks example, the stub, the API reference (extension docs and `docs/MICROPYTHON_API.md` §6a), the blocks reference, `help()`, two snippets (`evn-drivebase`, `evn-drive`) and `examples/09_drive_base.py`.

## 0.2.20 (2026-09-18)

- **Firmware 0.2.20: the pose estimator with an IMU on a real, moving robot.** With wheels and an IMU the prediction is now hybrid — speed from the wheels, yaw rate from the gyro, the gyro bias learned from the wheel difference whenever the robot is not turning. The plan's inertial speed prediction integrated the accelerometer, which under the running drive motors carries 1.4–1.9 m/s² of vibration (peaks 4–9 m/s²) against robot accelerations below 1 m/s²: the estimated speed jumped ±0.5 m/s, half the wheel updates were gated out, and every move ended 30–130 mm off. On the rig's floor moves (90° turns, 20 cm straights, 90° pivots, each returning to its start) every move is now within 6 mm of the encoders and turns in place within 1.2 mm (`docs/POSE_ESTIMATION_DESIGN.md` §6).
- **New `Pose(..., imu_offset=(x_mm, y_mm))`**: where the IMU sits, forward and left of the axle mid-point; a tape-measure value is enough. It removes the centripetal and tangential terms a turning body adds at a lever arm (used by the sets without wheels).
- **Filter robustness**: a wheel update that failed its χ² gate used to stay rejected for ever once the prediction had run away; after ten rejections running the speed prior is dropped and the wheels are taken (as the magnetometer update already did for the heading). The service's and the filter's angle wraps were `while` loops that never end on a huge or infinite heading; both are bounded now. `Pose._stats()` (bench diagnostic) exposes the gate counters.
- **Mounting note**: the filter takes the body frame the `IMU` / `Compass` objects publish, so a module's `axes(top=, front=)` must be set from its silkscreen before the `Pose` is built (the rig's IMU is upside down, `axes(top='-z')`; its compass has the chip's −x on top). A compass within about 10 cm of the motors reads the wheel angles (0.45 G in the heading plane per wheel turn) and cannot be calibrated or used as a heading source.
- **Encoders-only pose benched in the air** (three runs, every sample within 2.1 mm and 0.8° of the dead-reckoned encoders) and **bench scripts** `tools/bench/mpy_pose_wheels.py`, `mpy_pose_imu_offset.py`, `pose_wheels_metrics.py`; samples are kept in RAM and written to the board's flash after the motors coast (a flash write during a move stalls the 1 kHz motion loop for a sector erase).

## 0.2.19 (2026-09-18)

- **Firmware 0.2.19: no standing voltage on a stopped shaft after `run(0)`.** On a wheel-loaded EV3 Medium the breakaway assist could stay armed after a run (it re-armed against the run direction when the breakaway lurch carried the shaft ahead of the ramping reference, and its release only accepted motion in the assist direction) and could arm at the stopped `run(0)` reference; either way it locked out the hold state's rest decay and left 66 mV to 1.8 V on the stationary motor, with `speed()` and `load()` reading motion that was not there. The assist now arms only behind a moving reference, releases when the shaft moves away at speed, and does not arm at all at a stopped speed-mode reference. 12 of 12 `run(0)` settles end in the hold state at 0 to 0.11 V; the 64-move loaded set is unchanged at 64 / 64 within ±1° (`docs/ADRC_IMPLEMENTATION.md` §6e).
- **New `control.state()`**: `(reference_deg, x1_deg, x2_degs, x3_degs2, applied_mv, hold, assist)` — the controller's reference, the ADRC observer's three states, the applied voltage and the two flags, a 1 kHz diagnostic for tuning and benches.
- **MPR121 touch array and ADS1115 ADC re-benched on the board** (the touch module under the running motors): 137 / 137 and 68 / 68 after five stale bench expectations were brought up to the 2026-09-18 audit; no false touch and no ADC pickup through every motor phase. Bench scripts `tools/bench/mpy_touch_excitation.py`, `touch_excitation_metrics.py` and `run0_trace_metrics.py` added.

## 0.2.18 (2026-09-18)

- **Firmware 0.2.18: a `DistanceSensor` setting change during a long range no longer raises.** `timing_budget(1000)` followed by `timing_budget(33)` (or any setter while a long range was in flight) raised `OSError: distance sensor on port n gave no measurement under the new setting`, because the chip finishes the range in progress before it restarts and the wait was sized from the new setting alone. The wait now covers the previous period, so the call returns after about one second instead of failing. Found by re-benching the VL53L0X after the 2026-09-18 audit (45 of 45 checks without a target, 58 of 58 with one). This is also the first packaged firmware with `evn.Pose` (the pose estimator begun in 0.2.16's notes; the 0.2.15 build did not carry it).
- **The loaded rig validated** (two EV3 Medium motors driving wheels off the ground on ports 3 and 4, two free EV3 Large on 1 and 2, the IMU, the compass moved away from the motors, a VL53L0X, a Bluetooth module on Serial 2, LED strips on servo ports 1 and 4; `docs/resume/2026-09-18_loaded_rig_validation.md`): the same move set before and after `calibrate()` with the wheels on lands every one of 64 positioning moves within a degree with no overshoot in both runs, so the retune corrects `full_speed()` and the Mediums' `load()` reading but positioning was already at the profile's limit; the rig does not tilt measurably under the motors (the accelerometer sees the wheel motors as vibration of up to 3.5 m/s²); the compass in its new place deviates by at most 0.015 G with the motors running; `mpy_mpu6500.py` 106/106, `mpy_rgbled.py` 76/76 and 77/77 on servo ports 1 and 4 (two of its expectations brought up to the audit: a second `RGBLED` on an open port is refused, an LED re-exposed by a larger `count()` is off until set), `Bluetooth(2)` attaches and is ready. One finding left open: right after `run(0)` a wheel-loaded Medium's `speed()` and `load()` wander for up to half a second while the shaft is still.
- **The browser build's board protocol checked against the real board**: `node scripts/test_protocol.js --port COM7` passes every check (raw REPL, files, the console agent at 4 frames a second with the device list). The browser's own port chooser needs a click; the owner did that step in Edge at <https://evn.coresg.tech/ide/> and saw firmware 0.2.18 and the battery updating live.
- New bench scripts: `tools/bench/mpy_loaded_moves.py` (a positioning and speed-step set sampled with the IMU and compass at 200 Hz) and `tools/bench/loaded_moves_metrics.py` (rise, overshoot, settle, final error, speed-step metrics, IMU and compass deviation, before/after tables).

## 0.2.16 (2026-09-18)

- **The extension has a tab in the activity bar.** *EVN ALPHA* (an ℕ glyph — the double-struck capital N of Cambria Math, U+2115) with three sections (*Board* and *Console* have a container of their own, see below). **Start**: five one-line rows — *New Python program*, *New blocks program*, *Board panel* (brings the board container up), *Documentation* (the online documentation at <https://evn.coresg.tech>) and *Getting started* (the walkthrough) — instead of the page of text it was, so the projects and the examples keep the room. **My projects**: the contents of your projects folder as a tree of folders and `.py` / `.evnblocks` files, following the disk by itself; the folder is created at startup (`EVN Projects` in Documents, or in the home folder when there is no Documents; the new setting `evn.projectsFolder` moves it) and carries `typings/evn.pyi` and a `.vscode/settings.json`, so *Open my projects folder as the workspace* gives Pylance autocomplete for `evn`. A file opens on a click (blocks files in the block editor), has inline *Run on the board* and *Upload as main.py* buttons, and Rename, Duplicate, Delete (to the Recycle Bin / Trash) and *Show in the file explorer* in its right-click menu. **Examples**: the eight bundled Python examples and, under *Blocks*, the eight block examples; they can be opened, edited and run (*Run example on the board*, or Ctrl+F5 in the editor) but never overwritten: a save asks for a name and writes a new program into the projects folder, with the tab switching to it, and *Save a copy to my projects* does that without editing first. Running an example saves nothing. New command *EVN: Open online documentation (evn.coresg.tech)*, which renders the same Markdown as the bundled `docs/`; *New project* is now *EVN: New project folder (examples, autocomplete stubs)* and the old save-dialog blocks command is *EVN: New blocks file here (choose a folder)*, both unchanged otherwise.
- **A *Board* section**, in the **secondary side bar** (its own container *EVN ALPHA Board*, which also holds the *Console* view below, so the board stays in sight next to the program; both views can be dragged anywhere else). **VS Code 1.106 or newer is now required** for it (`engines.vscode` is `^1.106.0`). The rows: the live console (below), the *Command line*, the port (click the row to choose another board), the firmware on the board against the build the extension brings (a warning row with an inline *Flash the firmware* button when the board is older, and a one-time offer to flash it), the battery (the pack is always two cells: the pack voltage and both cell voltages, a warning under 7.2 V and an error under 6.6 V), *Motors*, *Servo ports*, *Serial ports*, *I2C devices*, and *Files on the board* with `main.py` first and an inline delete button on each file. The header carries Send a command to the board, Read the board, REPL and Stop all motors, and in its `...` menu Connect / Pause the live console, Show the console output, Reset the board, Flash MicroPython firmware, List files on the board, Name this board, Collect board diagnostics and Select board port; when `mpremote` is missing the section shows an *Install mpremote* button instead. New commands *EVN: Read the board (firmware, battery, files)*, *EVN: Delete from the board* and *EVN: Configure what is connected to a port* (the tree only).
- **A live console to the board.** Whenever no program is running and the REPL is closed, the extension holds the port open through a small helper (`scripts/evn_console.py`, pyserial, which comes with `mpremote`): raw REPL, a soft reset that skips `main.py`, and a small agent on the board. The *Board* section then shows the motor angles and speeds of ports 1 to 4 four times a second, the pack and cell voltages, the standard peripherals on the I2C ports 1 to 16 identified by their **ID register** (re-scanned about every 5 s; anything else listed by address), the servo ports with what you said is plugged into each (Geekservo 270°, Geekservo continuous, generic 180°, an RGB LED strip, or nothing — the console creates the object, so the port is `s3` or `l3`), the files on the board, and a **Command line** row that runs one line of Python on the board (`m1`..`m4` the motors, `s1`..`s4` the servos, `bt1` / `bt2` and `u1` / `u2` the serial ports, `d5` the device on I2C port 5, `evn` imported; the answer goes to the new *EVN Console* output channel, and the last 20 commands are offered again). **A program the board started by itself from `main.py` is never interrupted**: the console row says the board is running its own program, its output is relayed to the output channel, and only the inline *Stop the board's program and connect* button ends it. The link steps aside by itself when a program runs, the REPL opens, files are uploaded, the board is reset or flashed, and comes back a second after the port is free. New setting `evn.console.enabled` (default on) turns it off; `evn.board.readOnConnect` is gone, because the console makes it unnecessary — *Read the board* still re-reads the firmware, the files and the I2C scan on request. New commands *EVN: Connect the live console*, *EVN: Pause the live console (free the port)*, *EVN: Send a command to the board*, *EVN: Show the console output* and the view-only *Stop the board's program and connect*. The helper's wire protocol is `docs/CONSOLE_PROTOCOL.md` in the repository.
- **A *Console* view under the *Board* tree.** The *EVN ALPHA Board* container now holds two views: the tree, and below it a prompt with a transcript on top of the same live console. Every line typed runs on the board in the live console's namespace, so variables persist from one line to the next and the objects are the ones the tree names (`m1`..`m4` the motors, `s<n>` / `l<n>` the servo ports, `bt<n>` / `u<n>` the serial ports, `d<n>` the device on I2C port n, `evn` imported). Enter sends, **Shift+Enter** adds a line so a small block goes over at once, Up and Down walk the lines sent before, **Ctrl+L** clears the transcript and Esc empties the prompt; while the console is not live the prompt is disabled and says why ("connecting to the board...", "the board is running its own program (main.py)"). The view mirrors the *EVN Console* output panel — the mirroring starts with the extension, so a line written while the view was closed is there when it opens. **It is not the mpremote REPL**: that is still the *REPL* button and its terminal, and *Open REPL* is in this view's title bar. New command *EVN: Clear the console view*.
- **The *Board* rows drive the board.** While the live console is connected, a configured port carries its own buttons, each of them one `call` or `exec` on the console; nothing is on a timer and no button is offered when the console is not live. A **motor port** with a model set on it (the gear: *EV3 Large*, *EV3 Medium*, *NXT*) has *Run this motor at a speed...*, *Run this motor to an angle...* (a speed, then a target; sent with `wait=False`, so the telemetry keeps flowing and the row counts the angle up while the motor turns) and *Stop this motor*. A **servo port** with a profile has *Drive this servo port...* — an angle for the 270° and generic profiles, a duty in percent for the continuous one, a colour pick for an RGB LED strip — and *Stop this servo port*. An **identified I2C device** has *Set a property of this device...* (a pick of that device's settable properties, taken from `stubs/evn.pyi`: the colour sensor's gain 1/4/16/60 or its integration time, the distance sensor's profile, the IMU's ranges, ... , then the value) and *Read this device live...* (a pick of what to read — `hsv`, `rgb`, `lux`, `distance`, `heading`, ... — after which the row shows the value four times a second, riding along with the telemetry; the eye-closed button stops it). These commands belong to their row and are not in the command palette.
- **A *Serial ports* section, and the whole extension over Bluetooth.** Serial 1 and Serial 2, each set with the gear to *EVN Bluetooth module*, *UART (raw serial)* or nothing; the live console then creates `bt1` / `bt2` or `u1` / `u2` on the board. **A UART header now carries its baud rate**: after *UART* the gear offers 9600, 19200, 38400, 57600, 115200 (the default), 230400, 460800, 921600 or *Other...* (any whole number from 300 to 3000000), the row reads `UART 9600 · 0 bytes waiting`, and a change reopens the port on the board at the new baud without losing the bytes it had queued. Headers set in an earlier version are read as they were, so nothing has to be set up again. A Bluetooth row shows the module's state, whether the board's REPL is on it and how many bytes are waiting, and carries three buttons: *Put the REPL on this Bluetooth module* (with an offer to *Make it permanent*, which adds `import evn` and `evn.Bluetooth(n).repl(True)` to `boot.py` on the board; only one module carries the REPL at a time), *Pair the Bluetooth module in Windows* (opens the Windows Bluetooth settings — the module shows as HC-05 or EVN Bluetooth, PIN 1234, and Windows then lists an outgoing "Standard Serial over Bluetooth link (COMxx)") and *Use the Bluetooth COM port for the board* (the port picker). With that done the USB cable can come out: the live console reconnects over Bluetooth in about 6 s with the same telemetry, and Run and the REPL work over the air. Verified on the bench over USB and over Bluetooth. New command *EVN: Pair the Bluetooth module in Windows*; the other two are row-only. Getting started §5a now leads with these buttons and keeps the by-hand route as the alternative.
- **The board follows the cable: Bluetooth when it is out, USB when it is in.** *Use the Bluetooth COM port for the board* now remembers that *Standard Serial over Bluetooth link (COMxx)* as the **wireless link** of the board it was picked for (the Bluetooth serial row says which: `link COM11`, or `no wireless link`), and `evn.port` keeps the board's USB serial number rather than a COM name. ## 0.2.15 (2026-09-18)

**Every one of the fifteen EVN Standard Peripherals is now bench-validated** (the per-device dates are in `docs/STANDARD_PERIPHERALS.md` §1). The documentation, the stubs, the snippets, the examples and the board's own `help()` no longer say "not validated on hardware" anywhere, and the stub's signatures were re-derived from the firmware bindings method by method — about a hundred of them disagreed with the C (a keyword the binding does not take, a getter typed as a setter, an `int` where the firmware returns a `float`, an optional argument shown as required).

**The I2C transport recovers by itself.** A transaction that timed out used to leave the RP2040's controller mid-transfer with bytes in its FIFOs, so the next read on that bus returned a stale byte and reported success (on the rig, a colour sensor's ID read 0x00 instead of 0x4D after a forced overrun). The layer now aborts, resets the controller, clocks a held SDA free with nine SCL pulses and a STOP, and re-initialises the bus after every timeout; it drops the multiplexer's channel cache after any failed transaction, so a multiplexer that lost its channel is re-selected instead of never; and it sizes the deadline to the transfer (1 ms + 40 µs per byte, at least 5 ms), so a long transfer no longer times out for being long. The three outcomes are now distinguishable from Python: `OSError(ENODEV)` — nothing answered at that address; `OSError(EIO)` — the device answered but refused a byte; `OSError(ETIMEDOUT)` — the bus was held and has been reset. `evn.I2C(port).stats()` reports `((errors, recoveries, stuck), (...))` per bus.

- **`evn.I2C`**: `scan()` never lists 0x70; 0x70 (the board's two multiplexers, which answer on every port) is refused on every port and 0x6A on port 16 (the battery charger) with `ValueError` — a stray write to either would have re-routed the whole bus or reprogrammed charging. `writeto()` takes 1..4096 bytes. New `stats()`. `_deadline(us)` is a private bench hook, documented as such.
- **`Compass`**: new `calibrate_cancel()` — a refused `calibrate_stop()` raises `ValueError` and **keeps collecting**, so a program can turn the sensor further and stop again, or give up cleanly. New `overrun()` (the QMC5883L's dropped-measurement flag) and `self_test(negative=False, raw=False)` (HMC5883L, at the gain the datasheet prescribes). `data_rate()` and `range()` return floats on both chips. `bias()` is refused below 4.0 Ga, where the strap saturates. The closed-object message is now `"Compass is closed"`, and a second `Compass(port)` on an open port keeps the calibration and the `north()` reference.
- **`Bluetooth` and `UART`**: new `readline(timeout=5000)` on both — the next line without its trailing `b"\n"` and without a `b"\r"` in front of it, or `None` on timeout; only the line leaves the receive buffer, so bytes that arrived behind it stay for the next `read()`. `timeout=0` never waits, a negative timeout raises `ValueError`, and a line longer than 255 bytes never completes: `readline()` times out and `overflow()` counts what was dropped. New `overflow()` on both (read-and-clear), and `UART.repl()` was missing from the stub.
- **`ColorSensor`**: `gain()`, `integration_time()`, `wait_time()` and `thresholds()` now return only once a sample measured under the new setting exists. `interrupt()` documented as `True` at the default persistence of 0 ("every cycle") — pass 1 or more for a flag that means "the clear count left the window".
- **`GestureSensor`**: `read_gesture(timeout=5000)` accepts the keyword the docs always promised (it raised `TypeError` before); a negative timeout raises `ValueError`. `status()[4]` is the chip's `GCONF4.GMODE` bit. `gesture_detail()`'s first three values are direction names or `None`, not integers.
- **`ADC`**: the default range is **±4.096 V** and the documentation no longer says ±6.144 V. `raw()`, `voltage()`, `read()` and `age()` take the input positionally.
- **`EnvSensor`**: documented that normal mode delivers a reading every measurement time plus the standby (40.5 ms at the defaults, ≈ 24.7 per second), while `measurement_time()` is the datasheet's worst case.
- **`TouchArray`**: the three `thresholds()` forms are documented as the binding implements them — `thresholds()` reads channel 0, `thresholds(3)` reads channel 3, `thresholds(12, 6)` sets every channel **including the proximity channel 12**, and `thresholds(3, channel=2)` raises `TypeError`. `overcurrent()` reports a fault seen since the object was opened, because the driver recovers from it by itself.
- **`Display`**: `text(col, row, s, invert=False)` accepts the keyword and returns the number of characters written; `on(enable=True)`, `zoom(enable=True)` and `all_on(enable=True)` take the argument optionally; `flip()` and `invert()` are getters as well as setters. Documented: the panel's RAM is not written while a hardware scroll runs (the first drawing call stops it and repaints, a new `scroll()` sends the stop first), `flip()` does not repaint, the constructor can take up to ≈ 740 ms on a freshly plugged panel, and `mirror()` is dropped by Ctrl-D.
- **`MatrixLED` / `SevenSegmentLED`**: `addr=None` picks the class default (0x71 / 0x74) and `addr=0x70` is refused with `"addr must be 0x71..0x77 (0x70 is the board's I2C multiplexer)"`. `SevenSegmentLED.number()` refuses an int outside −999..9999 and NaN / infinity instead of showing a saturated value; `MatrixLED.text(on=0)` is refused. The closed-object message names the class (`"MatrixLED is closed"`, `"SevenSegmentLED is closed"`) and a full pool says `"port %d: no free LED display slot (at most 4)"`.
- **`IMU`**: `tilt()` is documented with its real range, (−180, 180] on both axes, so an upside-down module is not read as level; `screen_orientation()` reports each event once; `dmp(rate=None)` keeps the rate in force; `stationary()` and `ready()` raise while the module is out; `settings(heading_correction=)` is clamped to 1..3600. The gyro filter values 250 Hz and 3600 Hz are refused (they select the chip's 8 kHz internal rate and break the DMP's time base), and an `evn.I2C` scan of the IMU's port pops one FIFO byte, which the driver heals.
- **`Servo.close()` and `UART.close()` are new.** A `Servo` object used to hold its channel until the next soft reset, so a program could not hand a servo port to an `RGBLED` strip (or re-open it with another profile) without Ctrl-D; a `UART` object held its serial port the same way. `close()` releases the claim on both — the servo's pulse stops and its pin goes low, the serial port keeps running and keeps its queued bytes — and every later call on the closed object raises `ValueError("Servo is closed")` / `ValueError("UART is closed")`. A second `UART` on a port an open object holds now says so (`OSError("serial port %d is already open")`), and a `Servo` constructor waits up to 10 ms for a just-closed strip to hand the channel back. `evn.I2C.scan()` also stops on a port whose probe timed out, instead of carrying the rest of the scan out against the bare bus.
- **`Servo` / `RGBLED`**: the servo channel has one owner — `RGBLED(n)` raises while a `Servo` object holds the port and the other way round; a servo port pulses nothing until the first `Servo` object is built; `disable()` is sticky but a new object drives its port again. `RGBLED`'s `invert` is keyword-only, and a blink or animate step below 2 ms is refused (the pattern is stepped by the 1 kHz poll).
- **Documentation and tooling**: `docs/API.md` and the README no longer describe the peripherals as pending a bench check; every peripheral snippet imports what it uses on its first line, and there are new snippets for the ADC, environment sensor, touch array, gesture sensor, LED matrix, seven-segment display, Bluetooth module and UART. `examples/08_standard_peripherals.py` was read against the bindings and every call that would have raised is fixed (`read_gesture(timeout=)`, `text(invert=)`, a seven-segment `text()` of letters the chip has no glyph for, an unguarded `calibrate_stop()`). The board's `help()` lists every class with its methods. The four block examples — `colour_line`, `spirit_level`, `compass_lights` and `bluetooth_grabber` — are named in the README and the getting-started guide, which also say that every peripheral has blocks.

Three sensors at the 2.4 ms default cost ≈ 20 % of the processor for their reads, which shows as slower prints; `integration_time(24)` cuts that ten-fold when 200 readings a second are not needed. Example 07 no longer stops with an error when the white/black calibration readings are identical.
- `DistanceSensor` bench-validated on three VL53L0X sensors at once (2026-09-17): every setting, the four profiles and the timing as the ST documentation says; the packaged firmware will include it from the next build. Two fixes: a sensor re-opened after `close()` (or after a board reboot following a `close()`) returned no distance and a nonsense ambient rate until it was unplugged and replugged — the firmware now resets the chip when it opens it; and a setting change that timed out once could leave the `DistanceSensor` object unusable — it now raises `OSError` and the object keeps working.
- `GestureSensor` bench-validated on the EVN APDS-9960 module (2026-09-17): colour, proximity, every setting and the gestures with a hand; the packaged firmware will include it from the next build. Gesture names are now the direction the hand moved with the module's label upright (`'up'` = bottom edge to top edge, as the EVN Arduino library names them; the datasheet's diode labels are mirrored on this module). A setter no longer leaves the object answering "not responding" until the next sample (every setter waits for its first reading under the new setting). Documented limit: a hand held still over the sensor keeps the chip in gesture mode and `proximity()` / `raw()` stop updating until it moves away (`age()` grows, `status()[4]` is `True`); use `engines(gesture=False)` to track a stationary object.
- `EnvSensor` bench-validated on the EVN BME280 module (2026-09-17): temperature, pressure and humidity with every setting, forced mode and the datasheet's noise figures; the packaged firmware will include it from the next build. Two fixes: a setter no longer leaves the object answering "not responding" until the next measurement (it returns once the first reading under the new setting exists, about two measurement times), and a negative value given to a keyword setting (`oversampling(humidity=-1)`) is refused with `ValueError` instead of being silently ignored — the same silent ignore was in `GestureSensor.gain()` / `led(boost=)` / `gesture_config()` / `photodiodes()`, `IMU.ranges()` / `filter()` and `TouchArray.thresholds()` / `electrodes()`, all fixed.
- `Compass` bench-validated on the EVN HMC5883L module (2026-09-17): every setting, the heading sign with a hand (clockwise viewed from above increases it), the on-board calibration with a 25 s tumble (residual 3.7 %, 22 of 26 directions) and its store/restore through `calibration()`; the packaged firmware will include it from the next build. Two fixes: `calibrate_stop()` on a sensor that was never moved used to *succeed* and install a nonsense calibration (its noise counted as coverage) — it now reports coverage 0 and raises `ValueError`, keeping the old calibration; and the HMC5883L delivered only 66 readings a second at its 75 Hz setting (one in eight skipped) — now every sample. A setter returns once the first reading under the new setting exists (two periods: ~30 ms at 75 Hz). Documented: the calibration corrects the sensor, not the room — the field changes as the module is carried past the EV3 motors' magnets; keep the compass at one place on the robot away from motors. The QMC5883L variant has not been on hardware yet.
- `SevenSegmentLED` bench-validated on the EVN seven-segment board (2026-09-17): every number, text and segment call checked against the chip's own memory and read by eye, unplug / replug with the number restored; the packaged firmware will include it from the next build. Three fixes: `SevenSegmentLED(port)` looked for the board at the wrong I2C address (0x71, the matrix's) and would never have found it — it now uses the board's 0x74 (`addr=` still overrides); `addr=0x70` (the board's own I2C multiplexer) is refused; `keys()` would have returned garbage because this chip mis-sequences a repeated-start read. A negative integer larger than 999 now shows `-999` instead of losing its sign. `MatrixLED` (the 8×8 board) has not been on hardware yet.
- `Display` bench-validated on the EVN OLED (2026-09-17; the panel is an SSD1315): every text and drawing call checked in the frame, the panel read by eye (logo, text grid, flip, invert, contrast, shapes, console scroll, hardware scroll, blink, zoom), unplug / replug with the picture restored by itself; the packaged firmware will include it from the next build. New: `Display.mirror(True)` copies the board's stdout — the REPL, every `print()`, tracebacks — to the panel, with or without a USB host.

## 0.1.4 (2026-09-16)

- Firmware: a motor holding position now pushes back against a load until it is back on target (before, a load could leave it standing several degrees off with nothing left to push with); a move whose shaft is held back waits for the obstruction instead of letting its reference run ahead, so `run()` no longer sprints to catch up when the load is removed (Pybricks behaviour: a blocked `run_angle(wait=True)` waits). Verified on two coupled motors of each model and on the free-shaft sweep.

## 0.1.3 (2026-09-16)

- Firmware rebuilt with the ADRC control law as the default (active disturbance rejection; self-calibrating, no per-motor tuning), `control.law()` to read or switch it (`"adrc"` / `"pid"`), and the observer at half bandwidth while holding at the endpoint (no more endpoint hunting on the EV3 Medium).
- Default limits at the fastest validated moves: acceleration 2400 deg/s² (EV3 Large) / 3000 deg/s² (EV3 Medium); a calibrated port's speed limit is its measured no-load speed when that is higher, so `run(100)` in percent mode is not clamped. The firmware caps every move at what the motor can do at the present battery voltage.
- `calibrate(wait=False)` starts a port without blocking; a later `calibrate()` on that port joins it, so several ports calibrate from one call.
- `done()` is true within 1° (was about 11°); `stalled()` / `load()` come from the ADRC's disturbance estimate (a calibrated unknown motor gets a working stall flag).
- `calibrate()` measures the motor's no-load speed as well (two-amplitude pulse test, about 4.5 s) and returns `(b0, tau_ms, v_break_mv, v_f_mv)`; a calibrated port's `full_speed()` is that measurement. `calibrate_speed()` removed (it duplicated `calibrate()`).
